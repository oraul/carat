# Design

## Context

Decision 15 of `tmp/briefs/pipeline-skeptic.md` replaces the periodic review inside the delivery (every five merges and after any REVIEW_AREAS change) and the queue items that pointed to backlog entries with a sprint model; decision 16 moves the broad quality points to the sprint-end review. Workflows cannot run a shell command or edit a tracked file: an agent start runs each command, and only the contributor commits.

## Goals / Non-Goals

Goals: a sprint of 5 self-contained queue items; a delivery that never reads the backlog; one `sprint-planning` run per sprint, ending at once when not due; grooming whose removals are mechanical and whose security removals are provable; the sprint's metrics row. Non-goals: the weighted token measurement (`ci-time`), the `reRaised` fix, the queue budget.

## Decisions

- Sprint boundaries live in `docs/sprints.tsv`: one row per planned sprint (`sprint`, `last`, `merges`, `changes`, `wall_min`, `min_per_change`, `total_tokens`, `over_budget`, `first_pass`), seeded with sprint 0 ending at `remove-commit-hooks`. `review-due` takes the last row's `last`, counts the `docs/metrics.tsv` rows after it plus the merged changes without a row (`pending`), and is due at 5; the combined diff starts at that change's merged commit; an even sprint adds the sweep. Counting rows, not run states, keeps it working on a fresh clone. Alternatives: a merge counter in the run state (lost with `build/`), git subjects (they do not say which merge was a change).
- The plan lands through the next package step. `sprint-planning` cannot commit, so its planner writes `build/plan/queue.md`, `build/plan/groom.txt`, optionally `build/plan/groomed.md` (the merged entries and the sprint findings it does not queue, which `groom` appends; never `build/plan/backlog.md`, which a delivery's planner replaces), and the marker `build/plan/sprint` naming the sprint. `groom`, run by the contributor's package step after `history`, applies it only when the marker names the sprint `review-due` counts, `docs/sprints.tsv` lacks it, and the run state `sprint-N` records its security review pass or blocked: it copies the queue, removes the entries, and appends the row computed from the sprint's metrics rows, which `history` has just completed. The planner starts only once the sprint security review and the skeptic returned, and while a plan waits without that record `review-due` stays due, so `/sprint` again reviews the sprint anew rather than closing it unreviewed. While a reviewed plan waits, `review-due` says not due (planned) and `plan-needed` reads the waiting queue, and a planner starting meanwhile starts from it, so nothing overwrites it. Alternative: a delivery of its own per sprint, a full run for a docs-only commit.
- `groom.txt` lines are `listed CHANGE HEADING` (an entry a merged queue item listed; CHANGE must be archived), `fixed COMMIT HEADING` (a commit of main that fixed it), and `duplicate HEADING` (one of the candidates `backlog-dups` printed, decided by the model; never a security entry). Every heading must match a backlog heading exactly; one bad line refuses the whole file and writes nothing. A security entry is one with any line naming `security`, so a disputed security finding stays until a fixing commit is named.
- The review over the combined diff: the security reviewer (Mode: sprint) and the quality reviewer (Mode: sprint, the broad points) return findings and record nothing; the skeptic (the quality reviewer, Mode: skeptic) gets both lists, records the quality findings it keeps and every security finding (`disputed: REASON` in front of one it disputes), and names what both missed. The record start then records `periodic-security` and `periodic-quality` of the sprint's run state from fixed words and counts, as `periodic-review.js` does. The sweep reuses `periodic-review.js` unchanged in substance.
- The delivery's close keeps reading `review-due` and notes "sprint-planning due" in its report; the Review phase goes. The REVIEW_AREAS case list goes with the triggers.
- The queue check: a `## Sprint` heading starts the sprint, a `## Pool` or `## Decisions` heading ends it; 1 to 5 numbered items, at most one whose parenthesis says `pipeline` without `T0`. A queue without the heading (the first sprint, whose items are already delivered) passes.
- The "never greps the backlog" case: a tools-test case fails when a delivery agent file (contributor, scout, checker, quality and security reviewers, benchmark, merger, retrospective) or `deliver-change.js` pairs `grep` or a read with `docs/backlog.md`.

## Risks / Trade-offs

- A sprint plan applied by a package step that never merges leaves the marker: `groom` runs again in the next package step, since `docs/sprints.tsv` on main still lacks the sprint.
- The planner's sprint mode reads the whole backlog (about 4,600 lines) once per sprint instead of greps in every delivery.
- `contributor.md` stays under its 8192-byte budget by removing the grep-free wording it no longer needs, without rewording untouched lines.
