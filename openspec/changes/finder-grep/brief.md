# Brief

finder-grep: a feature the user asked for (T2 user request, estimated medium, 2026-11-19: "Something that I really need it's the fuzzy grep in find files when I do space F F", then, asked whether paths or contents, "Search file contents", then "Can you priorize it?"), off docs/queue-feature.md pool item 23 at 32ea3a9, delivered now in the feature lane as a user-approved exception beyond Sprint 20, beside the backlog-lane delivery contributor-tier-routing; touch no file of the backlog lane (docs/queue-backlog.md, docs/metrics-backlog.tsv).

Problem: <leader>ff (plugin.finder.open) fuzzy-matches file paths only (carat/plugins/finder/matcher.rb); there is no way to find a file by what it contains.

Change, in the finder plugin (carat/plugins/finder/), requiring only carat/plugin_api.rb and its own files: a content search picker, action plugin.finder.grep, bound by the plugin's manifest defaults to <leader>fg and listed in the palette. Typing a query lists matching lines of the project's files as rows of path, line number and the line's text, fuzzy-ranked with Matcher's rules; reuse Matcher. The files are the finder's own listing; a file's text is read through existing host requests (no new host request, no API version bump). Picking a row opens the file with the cursor on that line (and the column of the first matched byte); the split, vertical split and tab keys work as in the file finder. File text is read once per open of the picker; each query's work is bounded (a cap on lines scanned and rows kept, 200 rows), a capped result says so on the prompt's row count; binary files, files over the host's read limit and very long lines are skipped or cut. Line text is untrusted: control bytes and invalid UTF-8 are shown safely. Streaming as a background task is not part of this change (finder-streaming and plugin-tasks, after spinel-bump).
