# Brief

plugin-lazy-activate: a user request delivered in the feature lane as Sprint 16's user-approved exception, beyond the sprint, right after vim-line-commands-b and before tab-close-d and vim-folds-b, one per lane; touch no file of the backlog lane (docs/queue-backlog.md, docs/metrics-backlog.tsv). The user asked that a plugin load only when first called ("if I call the file explorer, the first time it will be loaded only when I call it"), then made it the standard ("it is something by standard for any plugins, imagine it can grow a lot here"), and, told it gets harder with every plugin written assuming activation at startup, decided "prioritize for now". In the package step put under the Sprint 16 heading of docs/queue-feature.md exactly one line: "The user-approved exception: `plugin-lazy-activate` (T2 user request, estimated medium, beyond the sprint, the user-approved exception), Sprint 16's one exemption." so the sprint does not count it (tools/run_state.sh exception_item).
The change: every enabled compiled plugin is activated at startup (`carat/plugins/registry.rb`, the host's activate loop under `carat/use_cases/plugins/`), and git_signs runs git in `activate`. Startup is 11.7 to 13.7 ms with git_signs on or off (measured at 79b6b7c in a pty, 15 runs each, time to the first frame), so this is the rule for growth, not a fix for today's speed. Make a plugin activate on its first trigger, as the rule for every plugin: the host registers its keys, ex commands, filetypes, and events from its manifest without activating it, and activates it on the first key or action it binds, the first ex command it registers, the first buffer of a filetype it declares, or the first event it declares (git_signs once the editor is idle after the first frame, so git never runs before it); `activate` reads the current state it needs, so a plugin loses nothing that happened before; a plugin that raises in a late `activate` is disabled as today, the editor running on. Write the rule into `docs/architecture.md` section 9, `docs/plugins.md`, the plugin spec under `openspec/specs/`, and the `make new-plugin` template, so every later plugin follows it; the plugin API version moves by a minor step if the host contract changes. Accepted when editor tests show the explorer, finder, and ruby plugins not activated until their first trigger and working as today after it (`test/editor_explorer.rb`, `test/editor_tab_flows.rb` still passing), git_signs' git calls only after the first frame, a plugin raising in a late `activate` disabled with the editor running, and a startup figure before and after in the proposal's results.
