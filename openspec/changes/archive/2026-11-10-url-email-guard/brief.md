## The brief file: check every commit and pull request for URLs and email addresses

The user's now-request (T2, and it closes a hard-rule breach that recurred on #95, #96, #97, and #98): "a script to run on each commit and pull request to check any kind of URL and email in it". The planner places it right after the change running when it was asked (`jump-list`), ahead of the other navigation and UI items, since every later pull request benefits; it folds what it covers from `merge-gate-tidy` (the live body ungated, the squash message unchecked) and `content-gate-gaps` (the gaps in the content scan), and records the folds in the queue's Decisions.

## What exists (main at be4b63a)

- `tools/gates.sh` has a `content` gate (the added lines of every branch commit and the commit messages: no URL, no email but the co-author trailer's) and a `pr-body` gate, run before the push and the merge. Nothing runs at commit time, and nothing checks the pull request after it is created.
- The breach: after a pull request is opened, a "Generated by Claude Code" footer with a session link is added to its body by tooling outside the contributor's text. The package step removes it, but GitHub's edit history keeps it, and no check fails while it is there.
- `content-gate-gaps` (queue) lists scan gaps: a `++ ` line, a quoted `.env`, a binary file, unquoted and merge-resolution secrets, paths split unquoted.

## What to build (the proposal decides the details)

1. One scanner, `tools/scan_text.sh` or a mode of `tools/gates.sh`, the single source of the patterns the content and pr-body gates already use: any URL (a scheme followed by `://`, hosts starting with `www` and a dot, and bare host-and-path forms such as the claude host followed by `/code/...` and the GitHub host followed by a path; the forms are described rather than quoted here, since the scanner refuses them), any email address, and a Claude session id; the only exceptions are the co-author trailer `Co-Authored-By: Claude <noreply@anthropic.com>` and the Spinel clone address in the Makefile's `toolchain` target, as CLAUDE.md allows. It reads text from a file or standard input and prints each hit as `where:line: kind: the matched text`, exiting non-zero on any hit.
2. At each commit, local hooks under a tracked directory (for example `.githooks/`): `commit-msg` scans the message, `pre-commit` scans the staged added lines; installed by a `make hooks` target that sets `core.hooksPath`, which `make toolchain` and the contributor's setup run, and documented in CLAUDE.md's Commands and the README.
3. On each pull request, a CI job in `.github/workflows/` on `pull_request` events `opened`, `edited`, `reopened`, and `synchronize`: it scans the title, the body, every commit message, and the added lines of the diff, and fails naming each hit. Because it runs on `edited`, a footer added after creation turns the check red until the body is clean, and the merger cannot merge over it. Security of the job itself: the title and body reach the script through environment variables or a file, never interpolated into the run script (script injection), with `permissions: contents: read` only, on `pull_request`, never `pull_request_target`, and its actions pinned as the existing CI's are.
4. The merger and the package step treat this check like any CI job: red blocks the merge; the package step's footer removal stays, now verified by the check.

## Acceptance

- Cases in `make tools-test`: each URL form, an email, a session id, the two allowed exceptions passing, the trailer with any other email refused, a URL split across a wrapped line, text in a quoted string, a `++ ` line, and a binary file skipped with a note rather than read.
- The hooks refuse a commit message and a staged line with a URL, and allow a clean commit, in a case that runs them against a temporary repository.
- The CI job's script runs locally on a sample title, body, and diff (no network), and the workflow file passes the existing workflow checks; the first pull request after the change shows the job green.
- CLAUDE.md, the README, and the code map name the new files and the `make hooks` target.

## Where the footer comes from (the user's note)

The session-link footer is added by the harness's GitHub tool layer when a pull request is created through it, after the contributor's text is submitted; nothing in carat's repository or `.claude/settings.json` writes it, and the `attribution` setting does not reach it. So the guard cannot prevent it: its job is to turn the pull request check red on the `edited` event the moment the footer lands, so the package step's removal is verified and no merge happens over it. Do not search carat's scripts for its source.
