# Design

## Context

See proposal.md for motivation. Today there is no `carat/plugin_api.rb`, no `carat/plugins/`, and no `config/plugins.json`; `Dispatcher` answers "Not implemented" to any action outside its case, `ExecuteEx` answers `E492` to any name outside its case, `HandleKey` treats a value with two dots as a key sequence because `action_name?` allows exactly one namespace segment, the keymap is built in one call from the configuration, and `bin/carat-gen-config.rb` generates only the configuration mirror. The window layout of the previous change already supports fixed-width windows, but only splits the current leaf, never the edge of the tab page. `FilePort` has `list` and `stat` that nothing calls yet. `DisplayWidth` already answers 1 for the private use areas by falling through, without saying so.

The Spinel facts recorded by the earlier designs shape every representation here: inline RBS pins `Array[T]` only with a builtin `T`, so an array of program objects is `Array[untyped]` and is read through one method whose return signature re-types the element; a `Data` value read from `untyped` cannot be dispatched to, a `Struct` value can; a local holding two types widens a method for the whole program; block-form `Data.define` and `Struct.new` ignore inline RBS; an empty array literal is `Array[Integer]` unless stored through a writer after `super()` or returned through a signature; an empty array literal held in a local and passed to another method is copied; there is no reflection, no `const_get`, and no computed `send`; a method a subclass overrides cannot carry a return type, only `# @rbs` parameter lines or `# @rbs skip`. A probe against the pinned compiler confirmed for this change that a base class with overridable methods dispatches to a subclass constructed elsewhere, that `rescue StandardError` around such a call catches what the subclass raises, that a `Data` member typed `untyped` can hold a nested hash literal and be walked with `is_a?(Hash)` and `each`, that a `Hash[String, Symbol]` member pins, and that a method with the signature `() -> Array[untyped]` may build its result with `[]` and `<<`. Two facts came up while implementing: a signature naming `Array[Symbol]` is not applied ("names no type Spinel can pin"), so the manifest's event list is passed as `untyped` and read with `include?`; and a line array stored through a `Struct` writer after `super()` lost its slice assignment at run time in this codebase although the same shape worked in a probe, so `Buffer` keeps passing its original members to `super` and stores only the new members through writers. Three more came from diffing `make types` against `main`: `# @rbs @member` pins apply to a `Data` subclass as to a `Struct`, but only when the class body has at least one statement, so every API value carries pins and a small method, except the manifest's four hashes, because a pinned hash member refuses the empty literal a plugin passes for no commands or no options; a hash literal whose key is a constant reads as `Hash[untyped, untyped]` where a literal key reads as `Hash[String, String]`, so the hello manifest spells its action name out; and a `Hash[String, Symbol]` pin leaves the values `untyped`, which is harmless for the option types.

## Goals / Non-Goals

**Goals:**

- One file, `carat/plugin_api.rb`, with no `require` of its own, defines everything a compiled plugin sees; the lint test proves no plugin reaches past it.
- Every request and every response is a value; the host methods are the fixed table a JSON-RPC gateway can map method names onto for process plugins later.
- A plugin can never end the editor or leave a buffer half-edited.
- The explorer change can open its tree in a fixed-width side window with its own bindings using only this API.
- `make diagnose` stays clean and `make types` shows no new `untyped` member on the entities beyond the intended `Array[untyped]` lists.

**Non-Goals:**

- The process plugin gateway and the protocol document.
- `idle`, highlights, virtual text, prompts, child processes, selection and marks in the buffer view, and sign shifting on edits (all listed in the proposal with the change each arrives in).
- Reading the user and project configuration files; the host reads whatever configuration value the assembly receives.

## Decisions

### The API is one file of values and two base classes

`Carat::PluginApi` holds `MAJOR = 1`, `MINOR = 0`, `VERSION = "1.0"`, `EVENTS` (the eight symbols), and the `Data` values `Manifest`, `Event`, `Context`, `Command`, `Edit`, `Response`, `BufferView`, and `FileInfo`, plus the base classes `Host` and `Plugin`. The file requires nothing, so a plugin that requires only it cannot reach an entity, a use case, or a driver, and the lint rule is a path check. The alternative, letting plugins require `carat/domain/*` values such as `Position` and `Range`, was rejected because it makes every entity part of the API and because a process plugin could not share it.

`Manifest < Data.define(:name, :version, :api_version, :actions, :commands, :bindings, :events, :options, :option_types)` keeps every list as a builtin-typed collection so no member leaks `untyped`: `actions` is `Hash[String, String]` from action name to description, `commands` is `Hash[String, String]` from command name to abbreviation (empty for none), `bindings` is the JSON keymap shape, typed `untyped` and walked exactly as `Keymap.build` walks the configuration, `events` is `Array[Symbol]`, `options` is `Hash[String, String]` from option name to its default as text, and `option_types` is `Hash[String, Symbol]` with `:bool`, `:integer`, `:string`, or `:list`. Option values are text on both sides (`"true"`, `"3"`, a string, list items joined by newlines) because a typed option table under Spinel needs one accessor per type and the plugins of the next changes need only strings and lists; the host converts the configuration value after checking its type. The alternative of an `Array[untyped]` of `ActionSpec` and `OptionSpec` values read through typed accessors works, as `Layout` shows, but every manifest author would have to build them, and the hashes read better in a plugin.

`Event < Data.define(:name, :buffer, :window, :path, :row, :col, :detail)`: the event name, the buffer and window numbers, the path (empty for none), the cursor row and column (for `resize`, the rows and columns of the screen), and a detail string (the mode name for `mode_change`, empty otherwise). `Context < Data.define(:count, :register, :buffer, :window, :path, :row, :col)` is what `on_action` receives, `Command < Data.define(:name, :bang, :args)` what `on_command` receives, `Edit < Data.define(:from_row, :from_col, :to_row, :to_col, :text)` one charwise replacement with an exclusive end, `Response < Data.define(:ok, :message, :number, :lines)` the general answer (the number is a window number or a count, the lines are a listing), `BufferView < Data.define(:ok, :number, :path, :lines, :row, :col, :modified)` the answer to a buffer read, and `FileInfo < Data.define(:ok, :size, :mtime, :directory)` the answer to a stat.

Buffers are numbered by their position in the list from 1 and windows by their layout order in the current tab page from 1, with 0 meaning the current one. Positions are what the editor already has (`EditorState#buffer_at`, `Layout#leaf_number`), they need no identity table, and they match how `:wa` reports `E141` and how `<C-w>w` counts. The alternative, stable ids assigned by the host, needs a table that must be cleaned when buffers leave the list; it can be added later behind the same numbers.

### The host is a base class with one method per request, and a plugin gets its own link

`PluginApi::Host` declares one method per request, each raising `NotImplementedError` and annotated with `# @rbs` parameter lines as the ports are: `read_buffer(number)`, `edit_buffer(number, edits)`, `move_cursor(row, col)`, `open_scratch(title, side, width, lines, bindings)`, `set_scratch_lines(title, lines)`, `close_scratch(title)`, `focus_window(number)`, `open_file(number, path)`, `message(text, error)`, `set_status(text)`, `place_sign(number, row, icon)`, `clear_signs(number)`, `run_ex(text)`, `list_dir(path)`, `stat(path)`, `icon(name)`, and `option(name)`. The parameters are the request's fields and the return is the response value; for a process plugin the gateway will map a JSON method name to one of these in a `case`, the fixed table the architecture asks for. The alternative of one `call(request)` taking a single `Request` value with a `kind` and every field of every request was rejected: it needs one wide value with mostly unused members, every field typed for its widest use, and a `case` on the kind in the host anyway.

`UseCases::PluginLink < PluginApi::Host` is the concrete host, one instance per plugin, holding the plugin's name and the `PluginHost` use case; every method forwards to the use case with the name, so the use case knows which plugin owns a scratch buffer, a sign, a status segment, or an option without the plugin saying so. The use case is what the tests drive directly.

### PluginHost owns registration, routing, events, and requests

`UseCases::PluginHost` is constructed with the state, the `FilePort`, `OpenFile`, `CloseWindow`, and the leader, and later receives `ExecuteEx` through a setter, because `ExecuteEx` routes plugin ex commands to the host while the host runs ex command strings through `ExecuteEx`; the setter breaks the cycle at construction time and `run_ex` fails with a message if it was never set. It keeps `Array[untyped]` of `PluginEntry < Struct.new(:plugin, :manifest, :name, :enabled, :reason, :link, :options)` read through `entry(i) -> PluginEntry`; the plugin itself is typed `PluginApi::Plugin` so the calls to it are virtual calls on the base class, which the probe confirmed.

`register(plugin)` reads the manifest, runs `Domain::ManifestCheck`, and adds the entry enabled or disabled with the first rule broken as the reason. `activate_all(config_plugins)` reads the `plugins` object: an entry with `enabled` false leaves the plugin registered and disabled with the reason "disabled in the configuration"; otherwise the options are resolved from the manifest defaults and the entry's `options`, the plugin's default bindings are added to the editor keymap, and `activate(link)` is called under the rescue that disables a plugin. The assembly calls `register` for every plugin from the list it receives, `activate_all`, and then adds the configuration's `keymaps`, so the configuration always wins; `Keymap#add_all(keymaps, leader)` is the instance form of `Keymap.build`, which now delegates to it.

Routing: `Dispatcher` sends any action starting with `plugin.` to `PluginHost#action(state, name, command)`, which finds the entry by the second segment, reports "No plugin named x" or "Plugin x is disabled", builds the `Context`, and calls `on_action` under the rescue. `ExecuteEx` asks `PluginHost#command?(name)` before `unknown` and runs `PluginHost#command(state, ex_command)`, which matches the full name or the abbreviation and calls `on_command`; the plugin's own messages go through the `message` request, so the outcome returned to the command line is a success with no message. Names are matched with `start_with?` and a `case`-free scan over the entries, because there is no computed dispatch.

Events are produced by `PluginHost#observe(state)`, called at the end of `HandleKey#call` and `HandleKey#timeout`, and once after the assembly opens the start file. It compares the state with a snapshot kept in the host: buffers not in its known list produce `buffer_open` (the known list is `Array[untyped]` of buffers checked with `equal?`, since two unnamed buffers are equal by value); a current buffer whose `changes` counter moved produces `buffer_change` (`Buffer#set_lines` increments the counter, so every primitive counts and a plugin's own `set_scratch_lines`, which replaces the lines without the primitive, does not); a new cursor or a new current buffer produces `cursor_move`; a new mode `mode_change`; a new tab index or leaf id `window_focus`; and the quit flag `quit`, after which `deactivate` is called on every enabled plugin. Delivery is to every enabled plugin subscribed to the event, in registration order, under the rescue. `buffer_save` is sent by `SaveFile#write` through `PluginHost#saved(buffer)` because no state difference tells a write from a reload, and `resize` by `EditorAssembly#render` when the size differs from the last one. The snapshot is taken after delivery, so what a plugin changes while handling an event does not produce events, which keeps a plugin from feeding itself. The alternative, explicit emission from every use case, was rejected because `cursor_move` and `mode_change` have a dozen sources each and one diff covers them all.

Requests run against the state and the ports with every failure turned into a failed response: `read_buffer` reads `buffer_at` and the cursor of the current window when the buffer is the current one (otherwise row and column 0); `edit_buffer` validates the whole list (rows and columns inside the buffer, end not before start, ascending and non-overlapping) before calling `Buffer#replace` from the last edit to the first so earlier positions stay valid, then `clamp_cursors`; `move_cursor` clamps into the current buffer and sets `want_col`; `message` is `state.show`; `set_status` writes `state.segments[name]` or deletes it for empty text; `place_sign` resolves the icon through the table and stores the glyph in `Buffer#signs` and the plugin name in `Buffer#sign_owners`, both `Hash[String, String]` keyed by the row as text because a hash pins only with string or symbol keys; `clear_signs` deletes the rows the plugin owns; `run_ex` calls `ExecuteEx`; `list_dir` and `stat` call the port under a rescue; `icon` reads the option and the table; `option` reads the entry's resolved options.

### Scratch buffers are buffers with an owner, a title, and a keymap

`Buffer` gains the members `owner` (the plugin name, empty for a file buffer), `title`, `keymap` (`Keymap?`, nil for a file buffer), `signs`, `sign_owners`, and `changes`, filled through the writers after the short-arity `super` so the empty hashes take the pinned types; `Buffer.new(lines, path, line_ending)` keeps its signature. `scratch?` is `!owner.empty?`. The state's `modified_buffer` and `hidden_modified` skip scratch buffers and `release` drops a scratch buffer whenever no window shows it, so `:q`, `:qa`, and `:wa` never see one as unsaved work and a closed plugin window leaves nothing behind; `SaveFile#write` refuses a scratch buffer with `E382`, Vim's message for a `nofile` buffer; `ExecuteEx#write_all` skips them. The keymap lives on the buffer rather than in a host table because `HandleKey` already has the buffer in hand and the lookup needs no plugin name: `HandleKey#lookup(state, keys)` asks the buffer's keymap first and falls through to the mode's keymap when the answer is `:none`, which keeps `j`, `k`, and `:` working in a plugin window; the keymap is built with `Keymap.build` from the plugin's bindings with the editor's leader. `HandleKey#action_name?` now accepts one or more namespace segments.

The side window is `Layout#split_edge(window, size, first)`: when the root is a row of side-by-side nodes the new leaf is added at its start or end; otherwise a new row node becomes the root holding the new leaf and the old root, which takes the rest of the width minus the separator. It returns -1 when the root's width cannot hold the size, the separator, and the minimum of the rest, which `open_scratch` reports as `E36`. The window is created fixed-width before it is placed, so the first `arrange` already leaves it alone, and `fit` takes the difference from the old content. The alternative, splitting the current leaf as `:vsplit` does, puts the explorer next to whichever window was current rather than at the edge, which is not what a file tree is.

### The registry is generated text with one line per plugin

`config/plugins.json` is `{"plugins": [{"name", "path", "class"}]}`: the name as the configuration and the manifest spell it, the path to require relative to `carat/plugins/`, and the class to construct. `Domain::RegistrySource.render(config)` turns it into the text of `carat/plugins/registry.rb`: a require per plugin, `NAMES`, and `Registry.all` returning `Array[untyped]` built with `<<`. The generator writes it, and `test/config_sync.rb` renders it again and compares, so the generated file cannot drift; the renderer lives in the domain because the generator is a compile root a test cannot require. `bin/carat.rb` passes `Registry.all` to the assembly, and the harness takes the list as a parameter (`EditorHarness.with_plugins`) because the doubles layer may not require `carat/plugins/`; `EditorHarness.default` runs with no plugins, so every existing editor test is also the proof that the editor works with every plugin disabled. The lint rule allows `carat/plugins/registry.rb` to require `carat/plugin_api.rb` and any file under `carat/plugins/`, and a file under `carat/plugins/<name>/` to require `carat/plugin_api.rb` and files under `carat/plugins/<name>/` only.

### Icons are a domain table and an option

`Domain::Icons.glyph(name, set)` looks the name up in one of three `Hash[String, String]` tables and answers the empty string for an unknown name. The nerd table uses Nerd Fonts code points (folder U+F07B and U+F07C, file U+F016, link U+F0C1, circle U+F111, the diagnostic circles and triangle U+F057, U+F071, U+F05A, U+F0EB, and the Devicons and Seti glyphs for the file types), the unicode table uses U+25B8, U+25BE, U+2022, U+2192, U+25CF, U+2716, U+25B2, U+25C6, U+25C7 and the geometric shapes for the file types, and the ascii table uses `+ - . ~ * X ! i ?` and single letters. `Options` gains `icons`, a string checked against the three names, and `config/default.json` sets it to `nerd`. `DisplayWidth.of` answers 1 for U+E000 to U+F8FF and U+F0000 to U+FFFFD explicitly, before the wide ranges, and the icon test asserts it, so a later East Asian width table cannot widen them by accident.

### Rendering

`Window#gutter_width` adds two cells when the buffer has signs; `FramePresenter#paint_gutter` paints the sign glyph at the window's left column followed by a blank, then the number, with the sign column in the `LINE_NUMBER` highlight. `paint_status` shows the title of a scratch buffer in place of `[No Name]` and, on the current window only, the state's segments after two spaces, joined by one space, before the right-hand cursor text; segments are `Hash[String, String]` on the state in registration order, which Ruby hashes keep.

### Deferred pieces, recorded

`idle` needs the main loop to report a period with no input, which it cannot today because `InputController#pump` returns only whether to redraw; it arrives with the language services change, which gives the loop a timeout table. Highlights and virtual text need highlight group ids a plugin can own and a frame cell that can carry an overlay, which `Cell#hl` as one integer cannot; they arrive with the syntax highlighting change. A plugin edit is applied as one batch and will become one undo transaction when the undo tree lands. Signs stay on their row number when lines are inserted or deleted above them; the git signs change, the first to place many signs, shifts them.

### Tests

`test/domain_plugin_manifest.rb` runs the manifest rules over good and bad manifests; `test/domain_icons.rb` checks every name in every set, the set properties, the option parsing, and the private use area width; `test/use_cases_plugins.rb` drives `PluginHost` with test plugins defined in the test program: registration, refusal of a newer major, action and command routing, event order, every request including the refused transaction, and a plugin that raises; `test/editor_plugins.rb` runs the hello plugin over the harness with the registry, a test plugin that opens a scratch window with its own keymap and closes it with `:q`, the disabled configuration, and the all-disabled session; `test/adapters_frame_presenter.rb` gains the sign column, the segment, and the scratch title; `test/domain_layout.rb` the edge split; `test/domain_buffer.rb` the change counter and the scratch members; `test/use_cases_ex.rb` the `E382` and `:wa` cases; `test/config_sync.rb` the registry; `test/domain_keymap.rb` the plugin bindings below the configuration.

## Risks / Trade-offs

- [Buffer and window numbers move when the list or the layout changes] → documented in `docs/plugins.md`; a plugin reads what it needs in the same call and the explorer re-reads window numbers before each open. Stable ids can be added behind the same numbers later.
- [A plugin keymap is consulted in every mode] → it is built from the plugin's bindings per mode, so an insert-mode key is found only when the plugin bound it there; the fallback keeps the mode's bindings.
- [`observe` runs after every key] → it compares a handful of integers and walks a buffer list of a few entries; no allocation beyond the events actually delivered.
- [Events delivered mid-key by `SaveFile` reach a plugin before the key's own diff events] → recorded in the spec and the plugin doc; the order among the diff events is fixed.
- [`Array[untyped]` for entries, known buffers, and the plugin list] → every read goes through one method with a return signature, as `Layout#node` does, and `make types` is diffed against `main` for new `untyped` members.
- [The hello plugin is in every real session] → it sets no message and no segment until asked, so the smoke test and the startup screen are unchanged, and the configuration can disable it.
- [The registry file is generated Ruby that the compiler reads] → it is covered by `config_sync`, by the lint RBS check, and by every build.
