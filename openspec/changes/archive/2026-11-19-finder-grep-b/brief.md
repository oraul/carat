# Brief

finder-grep-b: docs/queue-feature.md Sprint 21 item 1 at ffe84f6, the user's Sprint 21 order (finder-grep, #229, was the user's "really need" feature; this is its follow-up), in the feature lane. Widened by the user (2026-11-19, after finder-grep merged: "the grep looks strange... it isn't filtering well... if I write Explorer... it should show everything that has explorer but isn't"). After the planner's split this change covers two defects of the grep picker; the per-key bound, the grep bench scenario, the bidi and zero-width code points in Grep.safe, and the private helpers are queued as finder-grep-c.

(1) Matching: today a line matches when the query's bytes appear in order anywhere in it (Matcher.span_score), so scattered letters match (a score of 0 is still a match), and the leftmost scattered span is scored, so a contiguous hit later in the same line ranks low. For content search, a line matches only when it contains the query as a case-insensitive (ASCII) substring; a query with spaces is several terms, and a line matches when it holds every term as a substring, in any order. Rank: a whole-word hit (a word boundary on both sides, Matcher.boundary? rules) above a part-word hit, more hits of the terms in the line higher, then a shorter path, then listing order. The file finder's path matching (<leader>ff, Matcher.score) is unchanged. The column is the first byte of the first term's hit. Update the delta spec, docs/plugins.md and the tests (scattered letters no longer match; a later contiguous hit is found; two terms in any order; whole-word ranked first; case-insensitive).

(2) Coverage: Grep stops loading at MAX_LINES 100,000 stored lines, but this repository's listing holds about 148,091 lines counting at most 1000 per file (the host's read_file row limit), so about a third of the files are never searched, and the results never say so. Raise the bound so a tree of this size is searched whole (for example 400,000 lines, with the memory this costs stated in the proposal), keep the 'capped' note on the prompt's count when a larger tree still hits it, and state in docs/plugins.md that a file is searched in its first 1000 lines (the host's read limit). The open-time read stays synchronous (streaming is finder-streaming's), so measure and report the open time on this tree in the pull request.

The plugin requires only carat/plugin_api.rb and its own files; no new host request. Out of scope: any edit of tools/rules.sh, docs/queue-backlog.md, docs/metrics-backlog.tsv, the bench, and the per-key bound.
