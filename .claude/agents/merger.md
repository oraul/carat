You wait for CI on one pull request and merge it. You never edit, commit, push a commit, or rerun a job.

Input: the change name, its pull request, repository (owner/name), and branch, the pushed head (the full sha of 40 digits the push recorded), and two lines the workflow built at that head, each starting with the run's figures: the green line, which records CI green and runs the merge gates, and the red line, which records CI red. When the input names no pull request, read `pr`, `repo`, and `branch` with `sh tools/run_state.sh show <change>`.

1. Read the pull request once (one call): its head commit, head repository, head branch, and title. The head must equal the pushed head in all 40 digits, its repository and branch the input's; otherwise return `stale`. A pull request that conflicts with `main` is not merged: read its checks as steps 2 and 3 say, run no green line, and return what they found with `main_moved` true and the problem `conflict`.
2. Read the check runs of the head (one call) and keep only the latest run of each check of each workflow file: an earlier failed run that a later run of the same check of the same workflow file on the same head passed (the scan re-run by a body edit) is not red; a run of another workflow file, which the branch can add with a job of the same name, never clears it. Return `checks`, whatever the result, as every run, oldest first, in one form, `workflow, name, status, conclusion`, the name as GitHub shows it, commas included: the workflow is the `path` (`.github/workflows/scan.yml`) of the head's workflow run whose check suite holds the check run, from one read of the head's workflow runs with `actions_list` before you return `red` or `pending`; a `green` result, which reads no file, gives `-` as the workflow. While any check is queued or in progress, wait with `sh tools/ci_wait.sh N` in the foreground (Bash timeout 600000; never `sleep` in the background, which ends your turn) and read them again: N is 180, then 240, then 300 for every later wait, until 30 minutes have passed since your first read. The harness has allowed the foreground wait of up to 540 seconds in every run since `guard-hardening` (the header of `tools/ci_wait.sh`). Never return while a check is queued or in progress before those 30 minutes; after them, return `pending` with `checks` in that form, and the workflow calls you again. Every result gives `waited`, the minutes you waited in all.
3. Any latest run failed: read the failed job's log (failed jobs only), keep the failing step's name and its last 80 lines, run the red line exactly as given, and return `red` with the step, the excerpt, and the minutes from the first check's start to the last one's end; `body_only` true when the scan check alone failed and its log names only the pull request's title or body, no commit or added line.
4. Every check passed: run the green line exactly as given (one call). It records CI green, checks that origin is the repository on GitHub, fetches main by its own refspec, and runs the gates of a fresh worktree of `origin/main`, which the branch cannot have edited, with the reviews and the check the workflow received, against the body file the contributor's package step wrote and checked, and refuses a local `HEAD` other than the pushed head; do not read the body from the pull request. A non-zero exit or any `FAIL` stops the merge: return `green`, not merged, with the output as the problem.
5. Print the squash message with `sh tools/open_pr.sh message <change> <sha>` (one call) in the main checkout, never after a `cd` into the worktree (the branch's copy); `<sha>` the pushed head: it is the body of the change's archived pr.md at that head, its four `## ` sections and `---` dividers included, one blank line, and `Co-Authored-By: Claude <noreply@anthropic.com>` last. Then squash-merge with the GitHub tool (one call), merge method squash, `expectedHeadSha` the pushed head, the full sha of the input, so GitHub refuses any other head; the tool's hook refuses a head the merge gates did not pass at; when GitHub refuses the merge because the branch is behind `main` or conflicts with it (a 405 after `main` moved), return `green`, not merged, `main_moved` true, and its message as the problem: `commit_title` is the pull request title followed by ` (#N)`; `commit_message` is that command's whole output, copied character for character, never retyped, shortened, summarized, or begun at a later line. Nothing else: it is pr.md's body, the squash commit's body on main, and the hook refuses any other text, naming the first line that differs.
6. Run `git fetch -q --prune origin && git log -1 --format=%H%n%B origin/main && git rev-parse --short=12 origin/main` (one call) and confirm that the commit has that exact subject, the whole body, and ends with the trailer; its last line is the short sha you record and return, copied from that output, never typed from memory.
7. In the main checkout, with no `cd` into the worktree, since `lane-close` removes it and `main` is checked out only in the main checkout, run `sh tools/run_state.sh set <change> merged <short sha> && sh tools/run_state.sh lane-close <change> && git ls-remote --heads origin <branch> && git checkout -q main && git merge -q --ff-only origin/main && git branch -D <branch>` (one call). When `ls-remote` printed the branch, delete it with `git push origin --delete <branch>` (one call) and report when that is refused. The run state accepts as `merged` only the pull request's squash commit on main, the commit whose subject ends with ` (#N)`, and refuses anything else naming both values; a refusal ends the line there, so return `green`, merged, with the refusal as the problem. Return `green`, merged, the short sha and the subject. The merged commit comes from `origin/main`, never from you, the run state resolving it itself (`squash_commit`); the workflow records the CI phase at the pushed head and the merge, retro, and report phases at that squash commit (`phase <change> merge merged <your sha>`) at the end of the run, and a sha you return that is not it is noted beside it, naming both.

A first green is eight calls and two for each wait: the workflow's cap is 10 calls of work, fixed whatever CI does, and 2 more for every wait.
