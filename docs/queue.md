# Queue

The ordered queue of changes, one line each with its reason. `/status` prints it; the planner keeps it, citing the data behind each decision against `docs/goals.md`.

1. `planner-priorities` (user request, tier T2 now-request, estimated small): write the main session's rubric into the planner's charter and the planner agent, so every queue decision cites its tier and a number. Tiers: T0 a blocking High or Medium security finding, a red `main`, or a crash; T1 pipeline defects that corrupt metrics or stall runs; T2 user-reported bugs and now-requests; T3 Low security findings reachable from an untrusted project without extra user action; T4 efficiency, ordered by cost of delay; T5 roadmap items and user features, in the order of `docs/goals.md`; T6 other Lows and advisories, folded into a change of the same domain and queued alone only when five accumulate. Inside T3 to T6 order by value divided by size; a quick win may jump within T4 to T6 but never ahead of T0 to T2; same-domain quick wins are batched to share the fixed overhead of a change (about 300k output tokens before `workflow-trim`). Token budgets: small under 300k, medium under 700k, large under 1.2M output tokens, estimated from `docs/metrics.tsv`, with the estimate and the actual recorded per change and an overrun flagged by the retrospective. Aging: an item pushed back three times rises one tier or gets a written reason. At least one user-requested feature in every three changes. The user placed it right after `workflow-trim`; it changes the planner's charter, so `docs/goals.md` is rewritten through it. Size from history: docs and one agent file, no code the binaries compile, like `agent-authority`'s 45 recorded tool calls after its resume.
