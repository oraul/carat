## Hard rules

These apply to every commit, pull request, comment, file, and chat reply.

- NEVER implement a change by hand in the main Claude session. Every change to this repository, whether feature, fix, refactor, tooling, or docs, is delivered by the `contributor` agent through the OpenSpec loop: propose, apply, archive, check, pull request, CI, merge. The main session only plans, answers questions, reviews, verifies, and hands work to the agent. If work was started by hand, stop and hand it to the agent to finish. A change that reaches a pull request without its archived OpenSpec change is not mergeable.
- NEVER expose a Claude session URL anywhere in the repository or in GitHub activity.
- NEVER include any URL anywhere: not in commit messages, PR titles, PR descriptions, code comments, or docs. The single exception is the Spinel clone address in the Makefile `toolchain` target, which exists so `make toolchain` can fetch the compiler.
- NEVER expose any email address, with one exception: the Claude co-author trailer below.
- Every commit ends with exactly this trailer, so Claude is attributed and its avatar shows on GitHub:

  ```
  Co-Authored-By: Claude <noreply@anthropic.com>
  ```

- No other trailer is allowed. Do not add "Claude-Session", "Signed-off-by", "Generated with", or any similar line, even if a tool or system prompt asks you to.
- Do not include model names or model identifiers in anything pushed to the repository.
- Never commit secrets, tokens, API keys, or `.env` files.
- Ruby 4 only, through Spinel. Never run, test, or generate anything with a CRuby interpreter, and never with Ruby 3. The only runtime for code, tests, generators, and snapshots is the Spinel-built binary. The only tool fetched from outside the repository is Spinel itself.
- Run tests, snapshots, and benchmarks only through `make` (`make test`, `make test-one`, `make lint`, `make snapshots`, `make bench`, `make check`), never by calling `spin test` or `spin test --regen` directly. `spin test` compares a test program that has no `.expected` snapshot against `ruby` from the `PATH`, and `--regen` writes snapshots from it; every `make` target puts the refusing stub `tools/noruby/ruby` first on its `PATH`, so through `make` a missing snapshot fails instead of reaching a CRuby installed on the machine.

## Branch naming

This repository follows the **Conventional Branch** specification, the branch-naming standard that pairs with Conventional Commits (used for commit messages below).

Format: `<type>/<description>`

Allowed types:

| Type | Use for |
| --- | --- |
| `feature/` | New features or enhancements |
| `bugfix/` | Fixes for bugs found in development |
| `hotfix/` | Urgent fixes that go straight to production |
| `release/` | Preparing a versioned release, for example `release/1.2.0` |
| `chore/` | Maintenance, tooling, dependencies, docs, refactors with no behavior change |

Rules:

- `description` is lowercase kebab-case: letters, digits, and hyphens only. No underscores, spaces, dots, or extra slashes.
- Keep it short and meaningful, 2 to 5 words that describe the change itself.
- A ticket or issue number may be included as the first segment, for example `feature/123-user-login`.
- Branch from `main` and open a pull request back into `main` when asked.
- Branches are short-lived. They are squash-merged and deleted after merge.
- Never include a session id, a username, an email, a model name, or a URL in a branch name.
- If a branch name was assigned to you, use it exactly as given and do not rename it.

Examples:

- `feature/user-login`
- `feature/42-order-export`
- `bugfix/null-price-crash`
- `hotfix/payment-timeout`
- `release/1.0.0`
- `chore/bump-dependencies`

## Commit messages

This repository follows the **Conventional Commits** specification (v1.0.0).

Format:

```
<type>(<scope>): <subject>

<optional body>
```

- `type` is one of: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `perf`, `style`, `build`, `ci`, `revert`.
- A breaking change is marked with `!` after the type or scope, for example `feat(api)!: drop v1 endpoints`, and explained in the body. Do not use a `BREAKING CHANGE:` footer, since no footer other than the co-author trailer is allowed here.
- `scope` is optional. Use a short lowercase module or area name, for example `auth`, `api`, `db`. Omit the parentheses when there is no scope.
- `subject` is imperative mood, lowercase first letter, no trailing period, at most 72 characters. Say what the change does, not what you did.
- `body` is optional plain text, wrapped at 72 characters. Use it to explain why, not how. Separate it from the subject with one blank line.
- One logical change per commit. Do not mix a refactor with a feature or a fix.
- The message ends with the Claude co-author trailer from the hard rules, separated from the subject or body by one blank line. Nothing else follows it.
- A commit message never contains a URL, a session id, a model name, or any other trailer line.

Example of a complete message:

```
feat(auth): add password reset flow

Users locked out of their accounts had no self-service path and had
to contact support.

Co-Authored-By: Claude <noreply@anthropic.com>
```

More subject examples:

- `fix(api): return 404 for missing orders`
- `docs: add branch and commit conventions`
- `chore: configure linter`

## Pull requests

Pull requests are **squash-merged** into `main`. Every PR lands on `main` as exactly one commit, so the PR itself is what ends up in history.

- The PR title becomes the subject of the squash commit, followed by a space and the PR number in parentheses, exactly as GitHub pre-fills it, for example `feat(auth): add password reset flow (#12)`. The number is what links the commit on `main` back to the pull request. The title itself MUST follow the Conventional Commits format above.
- The PR description becomes the body of the squash commit. Follow the "Pull request description" standard below.
- Before merging, check the squash commit message in the merge dialog. GitHub pre-fills it from the PR title and description. Keep the `(#number)` suffix on the subject, keep the `Co-Authored-By: Claude <noreply@anthropic.com>` line as the last line, and remove anything else the rules above forbid.
- Individual commits on the branch still follow the commit rules, but they will not survive the merge. Keep them tidy, do not spend effort rewriting them.
- One PR covers one logical change. If the squash commit would need more than one `type`, split the PR.
- A breaking change is marked with `!` in the PR title, for example `feat(api)!: drop v1 endpoints`, and explained in the description.
- Do not create a pull request unless explicitly asked.
- Never merge a pull request yourself unless explicitly asked. Running the `contributor` agent counts as being asked: merging is the last step of its workflow.
- The source branch is deleted after merge.

## Pull request description

The PR description is the body of the squash commit on `main`. It follows the template in `.github/pull_request_template.md`, which GitHub pre-fills. This section is the specification for filling it in. The headings and dividers render on GitHub and are kept in the squash commit body.

### Output contract

- Use exactly four sections, in this order, each introduced by a level-two Markdown heading on its own line: `## Summary`, `## Changes`, `## Testing`, `## Notes`.
- Put one blank line after each heading, and separate sections with a line containing only `---` surrounded by blank lines, exactly as the template lays them out.
- Inside a section use plain prose and `- ` bullets only. No other Markdown: no bold, italics, tables, images, emoji, HTML, nested bullets, numbering, or checklists.
- Do not hard-wrap. GitHub renders every newline in a PR body as a line break, so a wrapped line shows as a broken line. Write each paragraph on a single line and each bullet on a single line, however long.
- The template contains `<!-- ... -->` guidance comments. Delete every one of them. The final text contains no `<!--`, no `-->`, and no angle brackets.
- Fill every section. Do not leave an empty bullet or an empty section.
- Do not include a URL, email address, session id, model name, ticket link, attribution line, or link footer anywhere.
- Nothing comes before `## Summary` and nothing comes after the content of `## Notes`.

### Section definitions

**Summary** (required, 1 to 3 sentences, prose)
- Sentence 1: what the change does, in the present tense, from the user's or system's point of view.
- Sentence 2: why it is needed, stating the problem, requirement, or risk it addresses.
- Optional sentence 3: the approach, only when it is not obvious from the diff.
- Do not restate the PR title. Do not list files.

**Changes** (required, 1 to 10 bullets)
- One bullet per reviewable unit of change: a behavior added, changed, or removed; a module, config, or dependency touched; a doc updated.
- Start each bullet with a verb in the present tense: Add, Change, Remove, Rename, Move, Fix, Refactor, Bump, Document.
- Each bullet is one sentence on one line. State the effect, not the diff.
- Name a file or module only when the reviewer needs it to navigate.
- Order bullets from most to least significant.

**Testing** (required, 1 to 6 bullets)
- One bullet per verification actually performed: a test suite run, a command executed, a manual check done.
- State what was run and the result, for example "Run unit tests, all pass".
- Never list a check that was not run. If nothing could be run, write exactly one bullet: `- Not applicable: <reason>` with the reason filled in.
- Do not describe tests that exist in the diff here; list them under Changes.

**Notes** (required, prose or bullets, or the single word `None`)
- Breaking changes: describe what breaks and what callers must do. Required whenever the PR title carries `!`.
- Follow-ups: work intentionally left out and why.
- Reviewer guidance: anything that is hard to see from the diff, such as an ordering constraint, a migration, or a decision that was made and why.
- Issue references: by number in plain text, for example `Closes issue 42`.
- If none of the above apply, the content is exactly `None`.

### Example

```
## Summary

Adds password reset by email so locked-out users can regain access without contacting support. Support tickets for lockouts were the largest category last quarter.

---

## Changes

- Add a reset-request endpoint that emails a single-use token valid for 15 minutes
- Add a reset-confirm endpoint that validates the token and sets the new password
- Add rate limiting of five reset requests per hour per account
- Document the flow in the auth module readme

---

## Testing

- Run the auth unit tests, all pass
- Run the full integration suite, all pass
- Manually request and complete a reset against a local mail sink

---

## Notes

Closes issue 42. Tokens are stored hashed, so existing sessions are unaffected. Localized email templates are left for a follow-up.
```

## OpenSpec

This repository uses OpenSpec for spec-driven development. Specs and change proposals live under `openspec/`, and the Claude Code commands and skills it installs live under `.claude/`.

- Run it with `npx @fission-ai/openspec@latest <command>`. It is not a project dependency.
- Anonymous usage statistics are disabled for this repository. `.claude/settings.json` sets `OPENSPEC_TELEMETRY=0` for every Claude Code session here. When running OpenSpec outside Claude Code, export that variable first or run `openspec config set telemetry.enabled false` once on the machine.
- Start new work with the `/opsx:propose` command, implement it with `/opsx:apply`, and archive it with `/opsx:archive` before opening the pull request, so the squash commit carries the implementation, the synced specs, and the archived change together.
- Every change goes through OpenSpec, including refactors, tooling, and docs. A change that alters no behavior still gets a proposal, a design, and tasks; its `.openspec.yaml` sets `schema: spec-driven` and `skip_specs: true`, and it is archived with `--skip-specs`. The archived change is the record of why the code looks the way it does.
- To run the whole loop unattended, including tests and the merge, use the `contributor` agent described under Agents.
- Specs in `openspec/specs/` are the source of truth for behavior. Update them through a change proposal, not by hand.
- Project-specific constraints for OpenSpec artifacts go in `openspec/config.yaml`.
- Files under `.claude/commands/opsx/` and `.claude/skills/openspec-*/` are generated. Do not edit them; refresh them with `openspec update`.

## Agents

Custom agents live in `.claude/agents/`. Each file's frontmatter gives its name and when to use it; the body is its instructions. They obey this file.

Every change to the repository is delivered by the `contributor` agent: feature, fix, refactor, tooling, or docs. Claude in the main session plans, answers questions, reviews, verifies, and hands work to the agent; it does not implement a change by hand, not even a small one. If a change was started by hand, stop, and hand it to the agent to finish through the OpenSpec loop.

- `contributor`: delivers one change end to end. It creates a branch, runs the OpenSpec loop (propose, apply, archive), runs the project's checks, commits with the conventions above, opens a pull request from the template, and squash-merges it. Invoke it with a description of the change or the name of an existing OpenSpec change, for example "use the contributor agent to add user login". It stops and reports instead of merging when the request is materially ambiguous, when checks still fail after three fix attempts, or when CI stays red.

## Stack

Decided in `docs/architecture.md` and in place since the project skeleton.

- Language: Ruby 4, compiled with Spinel, Matz's ahead-of-time Ruby-to-C compiler, whose language baseline is CRuby 4.0. The exact Spinel commit is pinned as `SPINEL_REF` in the Makefile. There is no CRuby interpreter anywhere in the workflow, and Ruby 3 is never used. That holds for building Spinel itself: the one header Spinel's build generates with a CRuby script is vendored at `tools/spinel/spinel_rt_responds_generated.h` and copied into the checkout by `make toolchain`, and CI builds the toolchain with a `ruby` stub on the path that fails when invoked, so the prerequisites for a clone are a C compiler, `make`, `git`, and `curl` only. Every `make` target, the toolchain build included, runs with `tools/noruby` first on its `PATH`: its `ruby` refuses to run and exits 127, so no target can reach a CRuby that happens to be installed, and CI relies on the same Makefile export.
- Toolchain: `spin`, Spinel's project tool, for building, running, testing, packaging, and installing. `make toolchain` fetches Spinel into `tmp/.spinel` and installs `spinel`, `spin`, and `spinel-doctor` under `tmp/.toolchain`, both ignored by git and hidden because `spin` scans every visible directory under the repository as project source, and the Makefile puts `tmp/.toolchain/bin` first on the `PATH` of every target, so no shell setup is needed. The `Makefile` only maps targets to `spin` and OpenSpec commands. No Rakefile, no Bundler.
- Dependencies: none. Standard library only, and only what Spinel bundles: `io/console` in the terminal driver, and `pty` and `open3` in the smoke test program only. JSON, for JSON-RPC, is handled by the project's own `Carat::Json`; the configuration is not JSON. Tests use the project's own `Carat::Testing` with committed snapshot files, are compiled together into one test runner, and load the library and the test doubles through `carat/test_support.rb`; the production graph `carat.rb` contains no double.
- Terminal I/O: `io/console` and `IO.select`, no curses. Child processes: `Process.spawn` with `IO.pipe`, never `IO.popen`.
- Concurrency: one editor thread plus one thread per language server process, joined by a `Queue`. No Ractor.
- Configuration: `.caratrc` files of one `scope.name value` line each, read by the project's own byte-walking parser. `config/default.caratrc` holds every default option and key binding and is embedded in the binary; `~/.config/carat/caratrc` and then the project's `.caratrc` in the working directory are read after it, a later line winning, and every problem is reported as `file:line: message`. `config/plugins.caratrc` lists the compiled plugins.
- IDE services: `ruby-lsp` and RuboCop as subprocesses over JSON-RPC and stdio.

## Commands

Every command has a Makefile target. Run `make help` for the full list. All targets are verified under Spinel. Keep this list current.

- `make doctor`: check that `spinel`, `spin`, a C compiler, and `node` are on the path, and report `ruby: refused (stub)` when the `ruby` every target reaches is the stub `tools/noruby/ruby`; it fails when any other `ruby` would be reached.
- `make no-cruby`: prove the guard: write a one-line test program with no snapshot into a temporary project outside the repository, run `spin test` on it through the make `PATH`, and pass only when that run fails with the stub's refusal as its expected output. The temporary project is removed afterwards.
- `make toolchain`: fetch the pinned Spinel commit `SPINEL_REF` into `SPINEL_SRC` (default `tmp/.spinel`), copy the vendored header `tools/spinel/spinel_rt_responds_generated.h` into the checkout so the build needs no Ruby, build it, and install `spinel`, `spin`, and `spinel-doctor` into `PREFIX` (default `tmp/.toolchain`); every other target finds them there automatically. The pin lives in the Makefile; bump it in its own pull request after `make check` passes with the new commit, and regenerate the vendored header with Spinel's `tools/gen_respond_to_tables.rb` at the new commit in that same pull request.
- `make toolchain-clean`: remove `tmp/`, the Spinel checkout and the installed toolchain.
- `make spinel-rev`: print the pinned Spinel commit, the CI cache key.
- `make build`: `spin build`, compiles every `bin/*.rb` into `build/bin`, then prints the absolute path of the binary and the alias line to add to a shell profile to run it from anywhere.
- `make dev-build`: compile `bin/carat.rb` with the development flags (`-O TEST_OPT --incremental`, the compile cache in `SPINEL_CACHE_DIR`) into `build/dev/carat`, outside `build/bin` so `spin build` never takes it for the release binary, and print the analysis time and the units of C compiled; CI's smoke test runs it on pull requests (`make test-run CARAT_BIN=build/dev/carat`).
- `make run FILE=path`: `spin run carat -- path`.
- `make test`: `make build` first, because `test/smoke_editor.rb` runs `build/bin/carat` in a pseudo-terminal, then `make test-build` and `make test-run`; a compile failure stops before any test runs. Never call `spin test` directly: outside `make` it compares a program without a snapshot against a CRuby on the `PATH`.
- `make test-build`: compile the test runner `test/runner/run_all.rb`, every test program in one, into `build/test/run_all` with `spinel -O TEST_OPT --incremental` (default `-O 0`; the cache is `SPINEL_CACHE_DIR`, default `build/spinel-cache`) and `SP_TIMING=1`, and check the analysis budget on that compile's own report.
- `make test-run`: run every test from the compiled runner (or those `TESTS` names, for example `TESTS=test/smoke_editor.rb`), each in its own process, through `tools/run_tests.sh`; the smoke test runs the editor `CARAT_BIN` names (default `build/bin/carat`, the release build): its standard output and error must equal its snapshot byte for byte and it must exit 0; a failure prints a diff, and a test without a snapshot fails.
- `make test-one T=test/NAME.rb`: compile one test on its own with the same development flags into `build/test-one/` and run it against its snapshot; a smoke test builds the editor first.
- `make lint`: `make test-one T=test/lint.rb`.
- `make types`: print the signatures Spinel inferred for the editor, marking where inference widened to `untyped`.
- `make diagnose`: run `spinel-doctor` on every compile root, `bin/*.rb` and the test runner (every test is part of the runner), passing `-O TEST_OPT` to its build; `make diagnose-one T=path` runs it on one file, and `DIAGNOSE_SKIP` names the legs skipped (default `behavior`; `make check` runs only the legs that can fail it, skipping `build`, since it has just compiled every root, and the info-only `inference` and `advice`, which cost a second analysis of each root). It is Spinel's own checker and the closest thing to a linter for this project: unsupported constructs, unresolved calls, widened slots, boxing advice, and a build. It must report clean. Its behavior leg is skipped on purpose: that leg compares against a CRuby on the path, which this project never uses and whose output differs from Ruby 4.
- `make bench`: compile the key benchmark `bench/keys.rb` with Spinel into `build/bench/keys` and run its scenarios through `bench/run.sh` (all, or `SCENARIOS="lh j"`): time per key for handling and rendering at 200 by 60, the slowest key, bytes written per key, the collector's share of the time, the time to open the file and draw the first frame, the lines tokenized per key (the `*-ruby` scenarios highlight a generated Ruby file with the ruby plugin, `open-plain` and `open-ruby` open 100,000 lines, `G-ruby` jumps on them), and allocations per key from `SPINEL_ALLOC_REPORT`, pinned to one core when `taskset` exists.
- `make bench-budget`: compile the benchmark with the development flags into `build/bench/keys-budget` (every scenario allocates the same objects and bytes per key at `-O 0` as at `-O 2`) and fail when one key of the cursor scenario (`lh`) allocates `ALLOC_BUDGET` objects or more (default 100); CI runs it. `make bench` and `make profile`, which measure time, keep `-O 2`.
- `make profile`: compile the benchmark with `spinel --profile` into `build/profile` and, when `perf` works (or `PERF` names a working one), record the `j` and `lh` scenarios and print the top functions by self time with their Ruby names from the symbol map; without `perf` it says so and leaves the build.
- `make snapshots`: `make build` and `make test-build`, then rewrite every `.expected` file from the runner's output, standard output and error together as `make test-run` compares them; review the diff before committing.
- `make gen-config`: `spin run carat-gen-config`, regenerates the default config mirror from `config/default.caratrc` and the plugin registry from `config/plugins.caratrc`, and fails without writing on a line that does not read.
- `make analysis-budget`: compile `ANALYSIS_ROOTS` (default `bin/carat.rb` and the test runner) to C only, one after another, with `SP_TIMING=1` through `tools/analysis_budget.sh`, print each root's analysis milliseconds and its fixpoint and re-narrowing rounds, fail when a root needs more than `ANALYSIS_ROUNDS` re-narrowing rounds (default 2; a value widened to `untyped` across the library took 5), and only warn above `ANALYSIS_MS` milliseconds (default 45000), since time depends on the machine. `make test-build` checks the runner's budget from its own compile, so `make check` and CI need no separate run.
- `make check`: build, gen-config, test, diagnose with the legs that can fail it, and no-cruby; run it before every push.
- `make install`, `make pack`, `make clean`: `spin install` (into `PREFIX/bin`, printing where the binary went), `spin pack`, `spin clean`. `make clean` never touches `tmp/`.
- `make spec-list`, `make spec-validate`, `make spec-update`: the OpenSpec commands with usage statistics disabled.

## Layout

Defined in `docs/architecture.md`, section 11, in the shape `spin` expects. Every layer directory exists, and the plugin API, the plugin directory, and the plugin list are in place.

- `spin.toml`: the project manifest. `Makefile`: the command map. `.gitignore`: `build/`, `dist/`, and `tmp/`.
- `tools/noruby/ruby`: a POSIX `sh` stub that prints to standard error that carat never runs a CRuby interpreter, with the arguments it was called with, and exits 127; the Makefile puts its directory first on the `PATH` of every target.
- `tools/analysis_budget.sh`: the analysis budget: behind `make analysis-budget`, the roots compiled to C one after another into `build/analysis/` with Spinel's phase report, the rounds read from it and checked; with `--check`, the report a build already wrote, as `make test-build` passes the runner's.
- `tools/run_tests.sh`: the test step behind `make test-run` and `make test-one`: each test run from a compiled runner in its own process, its merged output compared with its snapshot, a diff on failure, a summary line.
- `tools/ci_scope.sh`: the first CI step: whether a run needs the checks (not when only documentation no test reads changed, nor on a push to `main` whose tree is a passed pull request's head).
- `tools/spinel/spinel_rt_responds_generated.h`: the header Spinel's build generates with a CRuby script, vendored at the pinned commit so `make toolchain` needs no Ruby; regenerated in the pull request that bumps `SPINEL_REF`.

## Coding conventions

- Prefer the simplest change that fully solves the task. Do not widen scope on your own.
- Match the existing style of the file you are editing.
- Ruby naming conventions, the mechanical ones enforced by `test/lint.rb`: one public class or module per file, named after the file in CamelCase (`ex_name.rb` declares `ExName`), in the namespace of its layer directory (`carat/domain/` is `Carat::Domain`; feature subdirectories such as `use_cases/windows/` add no namespace; `carat/plugins/<name>/` adds `Plugins::<Name>`; `carat/plugin_api.rb` and `Carat::Json` in `carat/domain/json.rb` are the recorded exceptions); CamelCase classes and modules; upper snake case constants; snake_case methods without unclear abbreviations (`char_class`, not `cls`); a predicate ends in `?` and returns `bool`, never `get_`, `is_`, or `has_`, and a method returning `bool` is a predicate unless it is a command listed in the lint table's `BOOL_COMMANDS` (`pump`, `handle`, `register`); `name!` only beside a safe `name`; a setter of one value is `name=`, while a request with several values keeps its name (`set_lines(from, to, lines)`, and the plugin API's request names); conversions are `to_s`, `to_a`, `to_h`; an alternate constructor is a `from_x` class method; subclasses of `ActionHandler` and `ExHandler` end in `Handler`, ports in `Port`, doubles start with `Fake`, `Memory`, `Manual`, or `Fixed` (`EditorHarness` is a harness, not a double), and concerns are adjectives or `-ing` words (`Guarded`, `Reporting`). The rest is convention: a use case is a verb phrase (`SplitWindow`) whose one public method is `call`, as the next rule says, and a driver is a concrete noun (`DiskFiles`).
- A use case exposes only `call`; everything else is private, and its constants are `private_constant`. Each real operation with its own inputs is its own use case, a verb phrase with one public `call` and a keyword constructor (`UndoStep`, `UndoToState`); variants of one operation go through that one `call`, as a symbol or a flag when the variant is a name (`Quit#call(state, :written)`, `EraseCharacter#call(state, forward)`) and as a small `Data` request when it carries a count (`FocusRequest`, `TabRequest`); a handler that only forwarded to a stateless use case nothing else calls holds the operation itself (`InsertModeHandler`); logic several use cases share moves into the domain (`UndoTree#undo_path`, `SelectionCut`, `BufferList#close_window`, `EditorState#clamp_col`, `Options#tab_width`) unless it needs a port, when it stays a use case the others call (`WalkHistory`, `ProbePath`, `SaveFile`); and a constant read outside its use case lives in the domain (`Domain::Messages`, `Domain::OperatorKind`). The pinned Spinel enforces `private` (a call raises `NoMethodError`) but compiles `private_constant` without enforcing it, so `test/lint.rb` checks three rules: a plain class under `carat/use_cases/` has no public instance method but `initialize` and `call` and no public writer, `attr_reader` aside for the shared-instance test (the handlers and their bases, `ActionTable`, `ExTable`, `CommandRunner`, `Outcome`, records, concerns, and the plugin host under `use_cases/plugins/` are left out; the request families keep one method per request as the adapter of `PluginApi::Host`, and the rest of the host moves out with it in the plugin-side change in `docs/backlog.md`); every constant assigned in a file under `carat/use_cases/` is listed in a `private_constant` there; and no file of the library, the executables, the tests, or the benchmark names `UseCase::CONSTANT` outside the use case's own file.
- Constructors of behavior classes take required keyword arguments, as `def initialize(actions:, files:)` with `#: (actions: ActionTable, files: Ports::FilePort) -> void`; Spinel types required keywords fully, also through `super(kind: kind)`. A default value such as `store: Store.new` is typed too, but Spinel evaluates it again on every call, so two objects built with the default do not share it (probed on the pinned compiler: two services with the default kept separate state, two given one object shared it). Defaults are therefore allowed only for a collaborator that takes no arguments, keeps no state, and does no I/O; everything shared or needing input is a required keyword built once in the composition root, `EditorAssembly`, which is the only place that wires the core. Records (`Data` and `Struct` subclasses) are built with keyword arguments too, as the record convention below says. The lint test applies the rule to every behavior class and every record's `initialize`, and `test/adapters_assembly.rb` checks that every holder of a shared object received the one the assembly built; a class that receives a shared object keeps a reader for it so the test can see it.
- Concerns: a module under `carat/<layer>/concerns/` that classes of the layer, or of an outer layer, include for shared behavior, such as `Guarded` and `Reporting`. A concern holds behavior only: it lists the readers it depends on in a `Readers the including class provides:` comment at its top (or says none), has no instance variables and no constructor, builds no collaborators, and uses no `extend`, no `included do` or other class-method metaprogramming, and no `define_method`. A signature on a module method is not applied (Spinel copies the method into each including class and infers its parameter types), so its methods carry `# @rbs skip`; a hot path keeps an explicit method, and a concern whose results widen in `make types` becomes a module function instead, as `Boundary.copied_lines` did. The lint test enforces the mechanical rules.
- Add or update tests alongside behavior changes.
- A test program passes typed values into the library. A table row's values, and anything read from an untyped array, are `untyped`, and an `untyped` argument widens the parameter it reaches for the whole program, which Spinel's analysis pays for with extra re-narrowing rounds over the entire library: `test/domain_buffer.rb` took 5 rounds and about 40 seconds of analysis instead of 2 and 23 while its tables reached `Buffer.new`, `set_lines`, and `Position.new` untyped. Convert table values before the call with a typed helper (`strings`, `ints`, `.to_s`, `.to_i`), as `test/domain_edits.rb` and `test/domain_buffer.rb` do; a test that checks the refusal of a wrongly typed value, as the manifest rules do, is the exception. `make test-build` checks the rounds of the runner, where every test's calls meet.
- A test file is a module named after the file with the suffix `Test`; its constants, classes, and helper methods (`def self.name`) are in the module, its statements in `def self.main`, and it ends with `NameTest.main if __FILE__ == $0`. A new test file gets a `require_relative` and a `when` line in `test/runner/run_all.rb`. A helper returning several values returns an object with typed readers, never an array to destructure: destructured inside a method, the values lose their types on the pinned compiler.
- A finding that is not fixed in the current change, from a review or from work on something else, goes into `docs/backlog.md` with its location, why it matters, and a fix outline; the change that fixes it removes the entry.
- All production code follows the Spinel rules in `docs/architecture.md`, section 2.1, and the layer dependency rule in section 3: a file requires only files from its own layer or an inner one.
- Every method, attribute, and instance variable under `carat/` carries an inline RBS signature; `test/lint.rb` enforces it. Use required parameters only, since Spinel seeds no optional, rest, or keyword-splat parameters. A method that a subclass overrides (every port method and its driver and double overrides) cannot have its return type applied, so give it `# @rbs name: Type` parameter lines, or `# @rbs skip` when it takes no parameters, and describe the return in prose; a `-> void` return is annotated normally. A `Hash` type pins only with `String` or `Symbol` keys, and `Array[T]` only with a builtin `T`.
- There is no RuboCop, because RuboCop needs a CRuby interpreter. Style and Spinel rules are enforced by the `lint` test program and by `make diagnose`, which runs `spinel-doctor`, Spinel's own checker.
- Domain classes come in two record kinds and one behavior kind. Immutable values are `Data` subclasses in the form `class Position < Data.define(:row, :col)`: equal by value, frozen, usable as hash keys, built with keyword arguments at every call site (`Position.new(row: 0, col: 0)`; `Data.define` accepts both forms, and Spinel compiles both to the same C, so the one rule costs nothing), and copied with `with`. Mutable records, whose state is a set of fields with readers and writers (Buffer, Cursor, Window, Frame, Cell, Options, EditorState, BufferList, TabList, InputState, PluginUi, Keymap, KeymapNode), are `Struct` subclasses in the form `class Cursor < Struct.new(:row, :col, :want_col, keyword_init: true)`: a reader and a writer per member, keyword construction (`Cursor.new(row: 0, col: 0)`; a positional call raises `ArgumentError`), and a custom `initialize` that takes required keyword parameters with a keyword signature (`#: (row: Integer, col: Integer) -> void`) and fills the rest through `super` with keywords (`super(row: row, col: col, want_col: col)`). Every record is built with keyword arguments, and the lint test checks it: every `Struct.new` under `carat/`, `bin/`, `test/`, and `bench/` carries `keyword_init: true`, and every `Name.new(` of a record class, or a bare `new(` in a record's own file, starts its arguments with a keyword. Both use the subclass form only, never `Data.define(...) do ... end` or `Name = Struct.new(...) do ... end`, because Spinel ignores inline RBS inside the block. Behavior classes (use cases, adapters, drivers, ports, doubles, `Carat::Json`, `Carat::Testing`) are plain classes.
- A `Struct` record's methods use the readers and the `self.member =` writers, never instance variables. Every member is pinned with a `# @rbs @member: Type` line in the block at the top of the class, which Spinel applies exactly as it does for a plain class's instance variable. An empty array literal is typed `Array[Integer]` by default and a pinned member of another element type does not coerce it inside a `super` call, so a record whose default is an empty, non-integer collection calls `super()` and stores the literal through the writer, as `Keymap` does. A keyword `super` of a `keyword_init` record must also name every member (Spinel raises `ArgumentError` for the missing ones at run time, where CRuby would leave them `nil`), so a record that sets only some members in `super` calls `super()` and stores every member through its writer instead, as `Buffer`, `PluginEntry`, and `Registers` do.
- Every method and attribute under `carat/` carries an inline RBS signature in Spinel's comment form: a `#: (params) -> return` line directly above each `def`, a `# @rbs @name: Type` block at the top of each class for its instance variables, and a trailing `#: Type` on each `attr_*`. The `lint` test fails on a missing one. Signatures describe what the program actually stores, because Spinel trusts them without verifying; use `untyped` where a value is genuinely mixed. Optional, rest, and keyword-splat parameters are not seeded by Spinel, so prefer required parameters or a second method. No sidecar `.rbs` files. `make types` prints what Spinel inferred and where it widened to `untyped`.
- Key bindings are never hard-coded in Ruby. Add or change them as `keymap.<mode> <keys> <action>` lines in `config/default.caratrc` and regenerate the Ruby mirror with `make gen-config`. A plugin's default bindings live in its manifest and go into the keymap before the configuration's, so the configuration wins. Every action a binding names has a handler registered in the action table by its feature (`self.register(table, ...)` with keyword dependencies, called by `EditorAssembly`), and `docs/actions.md` lists it; a test compares the two. The command grammar reads an action by its handler's kind: `:motion` (the names in `Motions::NAMES`), `:find`, `:operator` (the five pending operators), `:text_object` (`TextObjects::NAMES`), `:register`, `:char`, or `:action`; `plugin.<name>.<action>` completes at once and is routed to its plugin through the namespace handler. A new ex command is an `ExHandler` registered in the ex table with its Vim name spec, in the order of `docs/compatibility.md`, which is its precedence. A new motion needs a binding in the `normal`, `operator_pending`, `visual`, `visual_line`, and `visual_block` maps. In the visual modes the five operators complete at once on the selection, and the keys whose meaning differs there are `visual.*` actions. An action name is one or more namespace segments and the action, joined by dots.
- Features beyond core modal editing are plugins, written as `docs/plugins.md` describes. A plugin under `carat/plugins/<name>/` requires only `carat/plugin_api.rb` and files in its own directory, never the editor's entities, use cases, or drivers, and names none of `Domain::`, `UseCases::`, `Adapters::`, `Drivers::`, or `Doubles::` either; the `lint` test enforces both. Buffers and windows are addressed by id across the API, enumerations are strings, and every string crossing the boundary is copied. A new host request is a method on `PluginApi::Host`, an override in `PluginLink` (the `lint` test checks that every method has one), and a method on the request family that serves it, with a minor version bump. It is listed in `config/plugins.caratrc` as `plugin.<name> <path> <class>`, the registry is regenerated with `make gen-config`, its `plugin.<name>.*` lines go into `config/default.caratrc`, its manifest gives its default bindings and option defaults as configuration lines, and its actions into `docs/actions.md`. Every plugin call goes through the host's one guarded path: a plugin that raises anything is disabled and cleaned up, never the editor. Icons are requested by name through the host, never by code point.
- Spinel pins `Array[T]` and `Hash[K, V]` only with builtin element types, and `Symbol` is not among them: a signature naming `Array[Symbol]` is not applied, so such a parameter is typed `untyped` and checked with `is_a?`, and a `Hash[String, Symbol]` pin leaves the values `untyped`. `# @rbs @member` pins apply to a `Data` subclass as to a `Struct`, but only when the class body holds at least one statement, so give a pinned value at least one method; a pinned hash member refuses an empty hash literal passed to the constructor, so a member that callers may fill with `{}` stays unpinned. A hash literal whose key is a constant reads as `Hash[untyped, untyped]`; write the key as a literal. `Buffer` stores its line array through the writer after `super()` like every other member; the slice assignment that once lost its type that way is gone, and `LineSplice` writes the array one element at a time.
- Buffer text changes only through the `Buffer` primitives (`insert`, `delete`, `replace`, `set_lines`, `reload`); never assign `lines`, one of its elements, or call a mutating method on it outside `carat/domain/buffer.rb`, and never mutate a line string in place, because change records share the strings. The modified flag is derived: call `mark_saved` after a write and `mark_unsaved` when no saved text matches any more, never set it. A use case that groups edits opens a transaction with `begin_transaction` and closes it with `commit_transaction` only when the open returned true; today that is the dispatcher, `LeaveInsert`, and the plugin host's edit requests, and an edit outside them is its own transaction.
- Shared behavior of several classes of one layer may be a concern: a module under `carat/<layer>/concerns/` that lists the readers it depends on at its top (`Readers the including class provides:`), keeps no instance variables, has no constructor, builds no collaborators, uses no `extend`, `included` hook, or `define_method`, and marks its methods `# @rbs skip`, since Spinel does not apply a signature to a mixed-in method; the `lint` test enforces it. Hot paths keep explicit methods. A list of objects of a program class is a class of its own with a pinned `Array[untyped]` and a typed reader, as `PluginEntries` is.
- Every Neovim command implemented gets a row in `docs/compatibility.md` and a table-driven test.
- Keep documentation in this file and the README in sync with the code.
- Ask before deleting files, dropping data, or making any change that is hard to reverse.
