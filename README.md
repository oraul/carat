# carat

A terminal IDE written in Ruby with Neovim's modal editing model, built, tested, and shipped with Spinel. `docs/architecture.md` holds the design and the roadmap; `docs/codebase-map.md` places every source file in its area; `CLAUDE.md` holds the commands and conventions.

Today it is an editor with split windows, tab pages, a plugin host, a file tree, and a fuzzy file finder: normal, insert, operator-pending, command-line, and the charwise, linewise, and blockwise visual modes (`v V <C-v>`, `o O gv`, every motion and text object, and `d x y c s > < J gJ p P r ~ u U X D C S R Y I A` on the selection); counts, the `"x` register prefix, and Neovim's `[count] operator [count] motion` grammar; the motions `h l 0 ^ $ f F t T ; , j k G gg + - _ w W b B e E ge gE ( ) { } H M L`; search with `/ ? n N * # g* g#`, also under an operator and in the visual modes; substitute with `:s`, `:&`, `&`, `g&`, and the ranges `% . $ N '<,'>`; the global commands `:g`, `:g!`, and `:v`, and `:d`; the text objects `iw aw iW aW is as ip ap` and the bracket and quote objects; the operators `d c y > <` with `dd cc yy >> <<` and `x s S C D Y J p P r ~`; undo and redo with branches (`u`, `<C-r>`, `U`, `g-`, `g+`, `:undo`, `:redo`, `:undolist`, `:earlier`, `:later`) and the dot command `.`; the unnamed, named, numbered, small delete, black hole, and read-only registers with `:registers`; insert-mode editing; the window commands `<C-w>s v h j k l w W p c o = q`, also with Ctrl held on `s v h j k l w p o q`, which wait for their second key however long it takes; `gt` and `gT` over the buffer tabs of the top row (`option.gt tabpages` gives them Vim's tab pages back), `<C-PageDown>`, `<C-PageUp>`, and `g<Tab>` over the tab pages, and `[b ]b [B ]B` over the buffers; scrolling with `<C-f> <C-b> <PageDown> <PageUp> <C-d> <C-u> <C-e> <C-y> zt zz zb` and the `scroll` option; and the ex commands `:w :q :wq :x :wa :qa :wqa :xa :e :sp :vs :new :vnew :close :only`, the buffer list commands `:ls :buffers :files :bnext :bprevious :bNext :bfirst :brewind :blast :buffer N :bdelete`, and `:tabnew :tabedit :tabclose :tabonly :tabnext :tabprevious :tabfirst :tablast`, with a tab page number for `:tabclose :tabonly :tabnext :tabprevious`. Ruby files are highlighted in color, and `:syntax on`, `:syntax off`, `:set filetype=`, and `:set syntax=` switch it. `:e` refuses a directory, a FIFO, a device, or a file over 64 MiB with Vim's message and keeps the current buffer. A file that is not valid UTF-8 opens with its bytes kept and written back as they were, `[ILLEGAL BYTE in line N]` naming its first such line and each illegal byte drawn as one U+FFFD cell. Compiled plugins add actions, ex commands, side windows, floating windows, and tokenizers through the API in `docs/plugins.md`; Escape in normal mode closes the topmost floating window, and `:q` or `<C-w>c` in a focused one closes it; the built-in `explorer` plugin, the file tree below, and the built-in `ruby` plugin, the Ruby tokenizer, are built on it. `docs/compatibility.md` lists every Neovim command it implements with its test, and `docs/backlog.md` the known items left for later changes.

## Building

The prerequisites are a C compiler, `make`, `git`, and `curl`. No Ruby interpreter is needed, not even to build the compiler, and none is ever used: every `make` target puts `tools/noruby` first on its `PATH`, whose `ruby` refuses to run, so a CRuby installed on the machine is never reached.

1. `make toolchain` fetches the pinned Spinel commit into `tmp/.spinel`, builds it, and installs `spinel`, `spin`, and `spinel-doctor` under `tmp/.toolchain`. Both directories are ignored by git, every `make` target finds the toolchain there on its own, and `make toolchain-clean` removes them.
2. `make build` compiles the editor to `build/bin/carat` and prints the alias line to add to your shell profile to run it from anywhere; `make install` puts it on the `PATH` instead.
3. `make check` runs the canonical stage list: the toolchain check, the documents' size and quality, the release and development builds, the generated config's freshness, every test against its snapshot, `spinel-doctor`, the `make no-cruby` proof, the allocation budget, the tests of the shell tools, and the rule gates; run it before every push. `make test-one T=test/NAME.rb` compiles and runs one test on its own. Run tests, snapshots, and benchmarks only through `make`, never with `spin test` directly: for a test program without a snapshot, `spin test` compares against the `ruby` on your `PATH`.

## Starting

`carat FILE` opens a file, or starts a new one when nothing is there. `carat` with no argument, or with a directory, starts on an empty buffer and shows the start screen: a gem forms from a point in about 0.6 seconds, a sparkle lights its top, and `c a r a t` appears with the keys to insert text, open a file, and quit. Any key ends it and does what it always does. `option.startscreen false` turns it off, `option.reducedmotion true` shows the finished picture without the animation, a terminal too small for the gem shows only the wordmark, and with the `NO_COLOR` environment variable set the picture is drawn in plain ASCII without colors of its own.

The cursor is a block in normal mode, a bar in insert mode, and an underline in replace mode, and the current window highlights the cursor's line (`option.cursorline false` or `:set nocul` turns it off). However carat ends, `:q`, a signal, or an error, the terminal gets its own cursor shape and its main screen back.

## Leader keys

The leader is Space. Its keys come in groups named by their first letter, and each group key waits for the next key however long it takes; Escape cancels it.

- `<leader>w` windows: `ws` split, `wv` split vertically, `wh` `wj` `wk` `wl` go to the window left, below, above, or right, `wc` close, `wo` keep only this one; a count works as with `<C-w>`.
- `<leader>q` quit: `qq` quits as `:qa` does, `qw` writes every changed buffer and quits as `:wqa` does.
- `<leader>f` files: `fs` saves as `:w` does; `ff`, like `<C-p>`, opens the fuzzy file finder: type to filter the project's files, `<C-n>` and `<C-p>` move, `<CR>` opens, `<C-x>`, `<C-v>`, and `<C-t>` open in a split, a vertical split, or a tab page, `<Esc>` closes, and a terminal of 100 columns or more previews the highlighted file in a box beside the list, the two sharing an edge under every `winborder`.
- `<leader>b` buffers: `bb` lists them as `:ls` does, `bn` and `bp` go to the next and previous one, `bd` deletes this one, or with a count the buffer of that number.
- `<leader>d` docs: `dp` pins the documentation float `K` opened into a split, `dd` peeks at the definition under the cursor in a float.
- `<leader>l` layout: `ls` hides the left sidebar and shows it again where it was, `lr` does the same for the right sidebar and `lp` for the bottom panel.
- `<leader>e` opens the file tree, as before.
- `<leader>p` (or F1) opens the command palette: every action and ex command with its description, dimmed, and its key on the right (a control key as `^W`), filtered as you type with the typed letters marked; Ctrl-N and Ctrl-P move the selection, Enter runs it, Escape closes it.

Pause after a group key, or after `g`, `z`, or `<C-w>`, and a panel centered at the bottom lists the keys that may follow and what each does, a group of your own named by the actions under it. `option.keyhints.delay` sets the pause in milliseconds (300; 0 turns the hints off), and `keymap.group <keys> <name>` names a group of your own, as `keymap.group <leader>w panes`.

Ctrl-S saves in normal and in insert mode, where you stay in insert mode.

In insert mode a completion popup lists the names the language server offers for the word before the cursor, matched fuzzily (`fn_na` finds `file_name`), each with its kind's icon and its type on the right: Ctrl-N and Down select the next, Ctrl-P and Up the previous, Enter inserts the item over what you typed, Tab replaces the whole word, and Esc closes the popup. The names come from the file type's language server when it offers completion: Carat asks it once you pause for a tenth of a second, without making a key wait, cancels a question about a word you have left, and fills the popup when the answer arrives. Without a language server, or before it answers, Ctrl-N and Ctrl-P complete the word before the cursor from the words of the open buffers, as in Neovim: Ctrl-N scans forward from the cursor through the current buffer and then the other buffers, Ctrl-P backward, and the words show in the same popup with the nearest selected, or `Pattern not found` when none matches. The selected name's documentation shows beside the popup, from the answer or asked for once the selection rests on it for a tenth of a second, once per name. In normal mode `K` asks the language server for the documentation under the cursor and shows it in a bordered float when the answer arrives; `K` again enters the float so the usual keys scroll it, `Esc` or moving the cursor closes it, and `<leader>dp` keeps it in a split. Both floats and the split draw the documentation with its headings, emphasis, code spans, links, and fenced code styled, the code highlighted like a buffer of its language when a plugin tokenizes the language the fence names (unless `:syntax off`), and plain with `NO_COLOR` set. Carat runs the terminal in raw mode, so flow control is off and Ctrl-S reaches it instead of freezing the screen. In normal mode `gd` asks the language server for the definition under the cursor and goes there when the answer arrives, opening its file; Ctrl-O goes back to where you were and Ctrl-I (Tab) forward again, through every position `gd`, a jump motion (`G`, `gg`, `%`, `{`, `}`, `H`, `L`, a search, `n`, `:N`), or a switch to another file (`:e`, `:b`, `:bn`, the finder, the explorer) left, each window keeping its own list as in Neovim, and Ctrl-^ or `:e #` shows the file the window showed before. Several definitions show a short list to pick from with Enter, a definition outside the project opens read-only, which no write takes, a jump to a file with no tab takes over the tab of the file you leave so the tab row does not fill up (`option.jumptab keep` keeps both, as Vim; the file left stays loaded, shown by `:ls!` and reached again with Ctrl-O or `:b N`), and with no server offering definitions or no answer you get Neovim's message. Typing `(` or `,` inside a call asks the language server for its signature, shown in a small float above the cursor with the argument you are at highlighted; it follows the cursor from argument to argument and closes when you leave the call or press Esc.

These keys moved: `<leader>w` used to write the file and `<leader>q` to quit the window. Press `<leader>fs` or Ctrl-S to write, and `:q` or `<C-w>q` to close a window, or `<leader>qq` to quit. To get the old keys back, add `keymap.normal <leader>w :w<CR>` and `keymap.normal <leader>q :q<CR>` to `~/.config/carat/caratrc`.

## Configuration

Carat reads its settings from plain text files of one setting per line, `scope.name value`: the first word is a dotted key, and the rest of the line is the value, a word, a number, `true` or `false`, or a list of words separated by spaces. A word containing spaces goes in double quotes (`\"` and `\\` inside them stand for a quote and a backslash), `#` starts a comment, and blank lines are ignored.

```
# ~/.config/carat/caratrc
option.number true
option.tabstop 2
option.theme carat-dark
keymap.normal <leader>e plugin.explorer.toggle
keymap.normal <leader>w :w<CR>
keymap.normal Q none
plugin.explorer.enabled true
plugin.explorer.width 30
plugin.explorer.ignore .git build tmp
plugin.finder.ignore .git build tmp node_modules
```

- `option.<name>` sets an option by its Vim name (`number`, `relativenumber`, `tabstop`, `shiftwidth`, `expandtab`, `autoindent`, `scroll`, `scrolloff`, `timeoutlen`, `undolevels`, `cursorline`, and the others), plus Carat's `icons`, `theme`, `background`, `startscreen`, `reducedmotion`, `breadcrumbs` (`auto`, `always`, or `never`), `jumptab` (`replace` as shipped or `keep`), `winborder` (the border of floats, Neovim's `none`, `single`, `double`, `rounded` as shipped, or `solid`, drawn with `+`, `-`, and `|` under `option.icons ascii`; every float has a column of padding on each side and its title centered on the top edge, as a notification's severity is, a float placed from the screen's corner keeps one cell from its edges and bars, the palette is centered again after a resize, and a float's text is never wider than the screen less its margin, padding, and border, so no row is cut), `indentguides` and `indentguides.char` (the indent guides of file windows, on with `┊` as shipped, `|` with `option.icons ascii`), and the slot sizes `layout.left_width`, `layout.right_width`, and `layout.panel_height` (0, the default, keeps the size a view asks for); `tabstop` takes 1 to 9999 and `shiftwidth` 0 to 9999, as in Vim.
- `keymap.<mode> <keys> <action>` binds keys in Vim notation in `normal`, `insert`, `visual`, `visual_line`, `visual_block`, `operator_pending`, or `cmdline` mode, or in the `completion` layer that answers first while the completion popup shows, to an action from `docs/actions.md` or to keys to replay, such as `:w<CR>`; the action `none` removes a binding. `keymap.pick <keys> <action>` binds in a pick list instead, as the definition pick list's `keymap.pick <CR> definition.choose`. `keymap.leader <Space>` sets what `<leader>` stands for.
- `plugin.<name>.enabled` turns a plugin on or off, and `plugin.<name>.<option>` sets one of its options.
- `language.<name>.lsp` and `language.<name>.formatter` name the commands the language services run: opening a file of a language whose `lsp` command is installed starts that server when Carat runs in a directory under a root of `language.trusted_roots` (for example `language.trusted_roots ~/src`, set in the user file, none by default), since a server such as ruby-lsp runs the project's own code; anywhere else the status bar reads `untrusted :LspStart` and `:LspStart` starts it. The bar shows the server's name and state (starting, indexing with a percent, stopped, or crashed, which `:LspRestart` restarts), and the server is told about the open files. Its diagnostics show as signs before the line numbers, the cursor line's message in the bottom row in normal mode, and the counts of errors, warnings, infos, and hints on the bar. A server's messages show as notifications at the top right, at most three, leaving after 3, 5, or 8 seconds by severity, and its long work (indexing) as a title and a progress bar on the status bar, which stays still with `option.reducedmotion true`; with `NO_COLOR` set both are drawn in ASCII without color. `:messages` shows the messages and notifications shown so far, and `:messages clear` forgets them. They are read from the defaults and the user file only, never from a project's file, so opening a directory cannot choose a program to run. For the same reason a project's file may bind keys only to actions and `none`, not to keys to replay.

The files load in order, and a later line wins: the built-in defaults (`config/default.caratrc`, every option and binding Carat ships, built into the binary), then `~/.config/carat/caratrc`, then `.caratrc` in the directory Carat starts in. Every line is checked when the files load; a mistake is reported as `file:line: message`, that line is skipped and the rest still applies, and the first problem shows in the message row when Carat starts, with the number of the others. A line holding a byte that is not UTF-8 is such a mistake. A configuration file that is not a regular file (a FIFO, a device) or holds more than 1 MiB, and a project's `.caratrc` that is a symbolic link, is reported and not read, so a cloned repository cannot hang or exhaust Carat at startup.

## Search

`/pattern<CR>` searches forward and `?pattern<CR>` backward, `n` and `N` repeat the last search in the same or the other direction, and `*`, `#`, `g*`, and `g#` search for the word under the cursor. Each takes a count, works after an operator (`d/foo<CR>`, `cn`) and in the visual modes, wraps around the buffer with Vim's "search hit BOTTOM, continuing at TOP", and the last pattern is in the `/` register. `<Up>` and `<Down>` at the `/` or `:` prompt recall earlier patterns or commands starting with what you typed.

- Patterns are Vim's magic patterns: `. * \+ \= \{n,m} ^ $ [a-z] \( \) \| \< \> \s \d \w \k \c \C \v \V` and the rest `docs/compatibility.md` lists; back references and look-around are not supported.
- `hlsearch` (on) highlights every match until `:noh`, `incsearch` (on) moves to the first match while you type, and `ignorecase` with `smartcase` ignores case unless the pattern has a capital letter; set them with `option.hlsearch false` in a configuration file or `:set nohls`, `:set ic`, `:set scs?`.
- A pattern can never hang Carat: one too large is refused with `E363`, and a search that would scan too long stops with a message.

## Substitute

`:s/pattern/string/` replaces the first match on the cursor line, and `g` after it every match: `:%s/old/new/g` changes every line, `:2,5s/a/b/` lines 2 to 5, and `:` in a visual mode starts the command line with `'<,'>`, the selected lines. A range alone moves the cursor (`:12`, `:$`). The string takes `&` for the match, `\1` to `\9` for the pattern's `\(\)` groups, `~` for the last string, `\u \U \l \L \e` for case, and `\r` for a line break.

- The flags `& e g i I n r p #` work as in Vim: `:%s/x//gn` counts the matches, `e` keeps quiet when there is none, and `&&` reuses the last flags.
- `:&`, `:s` alone, and `&` repeat the last substitute on the range or the cursor line, `3&` on three lines, and `g&` on every line with the last search pattern and flags.
- A substitute is one undo step, its pattern becomes the last search for `n`, and like a search it can never hang Carat: one that would work too long changes nothing and reports `E363`.

## Global

`:g/pattern/command` runs an ex command on every line that matches: `:g/TODO/d` deletes those lines, `:g/^#/s/x/y/` substitutes on the comment lines, and `:g/x` alone lists them. `:v/pattern/command` and `:g!` run on the lines that do not match. A range limits the lines (`:10,20g/x/d`); without one every line counts.

- A line is visited only if it matched before the command ran on any line, so lines a command deletes or inserts are never visited by mistake.
- `:[range]d [x] [count]` deletes lines into a register, the numbered registers shifting as with `dd`.
- A global is one undo step, its pattern becomes the last search for `n`, and like a search it can never hang Carat.

## Syntax highlighting

Carat highlights the files whose filetype a plugin tokenizes; the built-in `ruby` plugin covers Ruby: `.rb`, `.rake`, `.gemspec`, and `.ru` files, `Gemfile`, `Rakefile`, `config.ru`, and any file whose first line is a `ruby` shebang. Comments and their `TODO`s, keywords, definitions, constants, variables, symbols, numbers, strings with escapes and nested interpolation, percent literals, heredocs, and regular expressions get Neovim's standard highlight groups, and a construct that spans lines keeps its color on the lines that follow. Only the rows on the screen and the rows above them are ever tokenized, so a large file opens as fast as a plain one, and an edit re-highlights only until the colors after it are the same as before.

- `:syntax off` draws every buffer plain and `:syntax on` brings the colors back.
- `:set filetype=ruby` (or `:set ft=ruby`) highlights the current buffer as Ruby, `:set syntax=OFF` turns one buffer plain, and `:set ft?` shows the filetype.

The colors come from a palette, chosen by the `option.theme` line of the configuration: Carat's own `carat-dark`, the default, and `carat-light`, with a sapphire accent, or the other editors' `one_dark` and `dark_plus` (Visual Studio Code's Dark+) for a dark terminal and `one_light` and `light_plus` for a light one. Each palette has its own syntax colors and colors the status bar and its mode pill, the buffer tabs, the line numbers, the selection, the search matches, the messages, and the file tree's icons as well, and every text color in it is readable on its background and on the cursor line at WCAG AA contrast. The terminal keeps its own background unless `option.background theme` asks the palette to paint it, which needs a terminal that clears with the current background color, as most do.

```
option.theme light_plus
option.background theme
```

Carat writes 24-bit colors when the terminal sets `COLORTERM` to `truecolor` or `24bit` (most modern terminals do), the 256-color palette otherwise, and the 16 basic colors when `TERM` names a terminal that has only those, such as the Linux console (`linux`). To turn the Ruby highlighting off, add the line `plugin.ruby.enabled false`.

## File tree

Each tab page has a left and a right sidebar and a bottom panel. A plugin's view opens in one of them, under a header row naming the views opened there; a sidebar keeps its width and the panel its height when windows are equalized, and `<leader>ls`, `<leader>lr`, and `<leader>lp` hide and show them.

With two or more file windows each shows a winbar on its first row: its file's path and, when the language server offers document symbols, the class and method the cursor is in, as `a.rb › Foo › bar` (`a.rb > Foo > bar` under `option.icons ascii`), the current window's on the accent the selected buffer tab shares. `option.breadcrumbs always` shows it on a single window too and `never` turns it off.

`<leader>e` (Space, then `e`) or `:Explorer` opens a file tree in the left sidebar, 30 columns wide, rooted at the directory you started Carat in, with the current file revealed and marked; the same key focuses the tree when it is open and closes it when it is focused. `:ExplorerFind` reveals the current file in the tree. Inside the tree:

- `<CR>` or `l` opens a file in the window you came from; on a directory `<CR>` and `o` toggle it, `l` expands it, and `h` collapses it or goes to the parent.
- `s`, `v`, and `t` open the file in a horizontal split, a vertical split, or a new tab page.
- `a` creates a file next to the entry, or a directory when the name ends with `/`; `r` renames; `d` deletes a file or an empty directory after asking `y` or `n`. The name is typed on the command line, Enter confirms, Escape cancels.
- `R` refreshes, `H` shows dot files, `-` moves the root up, `C` makes the directory under the cursor the root, `q` closes the tree, and `?` shows these keys.
- `j`, `k`, `gg`, `G`, and the `<C-w>` commands work as in any window; `:q` in the last file window quits even while the tree is open.

The tree draws its folders and file types with the icons below, so it reads well with or without a Nerd Font. Its options live in your configuration:

```
plugin.explorer.width 30
plugin.explorer.side left
plugin.explorer.show_hidden false
plugin.explorer.ignore .git build tmp
```

`side` is `left` or `right`, `show_hidden` lists names starting with a dot from the start, and `ignore` names entries the tree never lists. Add `plugin.explorer.enabled false` to turn the tree off, and bind `<leader>e` to something else, or to `none`, to free the key.

## Icons and Nerd Fonts

The file explorer, the diagnostics, and the plugins draw small icons: folders, file types, error and warning markers. By default they come from a Nerd Font, a font family that adds thousands of such glyphs to a programming font. The font is optional: the editor is fully usable without one, see the `icons` option below.

To use the icons, install a Nerd Font and select it in your terminal. JetBrainsMono Nerd Font is a good choice.

- macOS: `brew install --cask font-jetbrains-mono-nerd-font`, then pick "JetBrainsMono Nerd Font" in the terminal's profile settings.
- Arch Linux: `pacman -S ttf-jetbrains-mono-nerd`.
- Other Linux distributions: download the `JetBrainsMono` archive from the Nerd Fonts project's releases, unpack it into `~/.local/share/fonts/`, and run `fc-cache -f`.
- Windows: install the font on the Windows side (unpack the same archive and select the font files, then "Install") and choose it in Windows Terminal's profile, so a terminal running Carat under WSL draws with it.

Then select the font in the terminal: in iTerm2, Terminal.app, Windows Terminal, GNOME Terminal, Konsole, Alacritty, WezTerm, kitty, and the others, the font is a setting of the profile or the configuration file; the terminal, not Carat, draws the glyphs.

Without a Nerd Font the icon cells show boxes or blanks. Set the `icons` option in your configuration to another set instead:

```
option.icons unicode
```

`unicode` uses triangles, bullets, and geometric shapes that common terminal fonts already have, and `ascii` uses plain characters such as `+`, `-`, `*`, and `!`. The default is `nerd`. Plugins ask for icons by name, so the option switches every icon in the editor.

## How carat is built with AI

Every change to carat, from a feature to a one-line fix, is written by Claude agents and goes through the same pipeline; a person decides what to build and reads the result. The pipeline is a workflow, `.claude/workflows/deliver-change.js`, whose phases are fixed in code, so no step depends on an agent remembering it. The mechanical agents, the scouts, the checker, the benchmark, and the merger, run on the cheapest tier, named by the `model:` line of their frontmatter; the others run on the session's model.

1. The planner orders the queue. Before a change starts, it reads the metrics history, the findings and proposals earlier runs left, and the goals, and writes the next `docs/queue.md` by the rubric of `docs/goals.md`: each item tagged with a tier, T0 (a blocking security finding, a red `main`, a crash) to T6 (advisories), and a size, small, medium, or large, a budget of total tokens, input plus output (and 25 minutes for a small change); each decision citing its tier and a number: a metric, a finding, or the user's request. A brief with more than about four separate fixes is split into balanced changes. The planner runs only when the queue needs a decision: a change other than the queue's head, a request beyond a change name, or a proposal or finding an earlier run left; otherwise the next item is taken as written. The queue is a sprint of 5 changes, at most one a pipeline change (a T0 security fix exempt), each item self-contained: its locations, why, a fix outline, the acceptance check, and the headings of the backlog entries it covers; the rest waits in its pool. A planned queue fits the byte budget of `docs/queue.md`, the planner reading the backlog only at a sprint's end. When a blocking security finding is still open, the run stops so its fix goes first.
2. Scouts read the code. For each area of `docs/codebase-map.md` whose files the change edits, at most three, a read-only scout writes a context pack of facts about the existing code the change edits or hooks into (files, methods, callers, tests, designs, the map's rules line) to `tmp/scout/`, and a pack still current at `main` is reused; when the brief is only the change name, the scouts and the contributor read its item in `docs/queue.md` themselves; no delivery reads or greps the backlog. Findings the change only records in the backlog reach the contributor as the planner's notes, not through a scout.
3. The contributor implements. It keeps the brief it was given and plans the change with OpenSpec (the brief, a proposal, a design, and tasks under `openspec/changes/`, archived together), starts each new file from its golden example in `docs/examples.md` or the `make new-*` generator that wires it in, reads the Spinel pitfalls once in `docs/spinel-notes.md`, writes the code and its tests, and commits as it goes. It is the only agent that edits the repository.
4. The checker runs the fast stages of `make stages` (`FAST_STAGES`) one by one, each with its log, in a throwaway clone outside the working copy, so branch code a stage runs cannot write the hooks, git configuration, or run states the gates read; CI runs the rest of `CHECK_STAGES` on the pull request, and the checker never edits. A stage it recorded counts only at the last check recorded in the run state, so a commit already checked is not checked again and a stage recorded at any other commit runs again. After a fix that changes only tests, it reruns only the test stages, the docs lint, and the gates and carries the others. The editor's development build, the test runner's build, and `spinel-doctor` are skipped when the code they read is the code of their last pass with the outputs it left, so a change to tooling or documents does not compile again what `main` passed; CI still compiles on any path but documentation. It refuses a tree with uncommitted changes. After a pass it notes the output tokens spent so far against the budget of the change's size, a sixth of its total-token budget, and the workflow records an overrun for the planner without stopping the run.
5. The quality reviewer reviews the committed diff for correctness and for a test beside every behavior change, the only points it blocks on, and notes the project's other rules (idiomatic Ruby within Spinel's rules, naming, the layers, simple code, docs currency) as advisories for the sprint-end review, beside the security reviewer on the same commit, so one fix round answers both. After a fix that changed only the files the blocking findings name, tests, and the records, it reviews only the fix and those findings. Each advisory finding is kept once as a note in the run state and is appended to `docs/backlog.md` with the change, so none is lost; only the sprint-end planning reads the backlog and clears its duplicates and the entries a merged item listed.
6. The security reviewer reviews the whole committed diff for vulnerabilities in every round. It is the most important gate: it can never be skipped, and a High or Medium finding it is confident in blocks the merge until it is fixed.
7. The benchmark: the check's `metrics` stage measures allocations and time per key and Spinel's analysis rounds, and `make metrics-compare` compares them with the figures recorded for `main`: those of the newest merged change without a row in `docs/metrics.tsv`, else its last row. When allocations and rounds are equal nothing more runs; otherwise the benchmark agent measures `main` itself: more allocations or rounds block, slower time is reported.
8. Whatever blocks goes back to the contributor, and every later phase runs again on the new commit, at most three rounds before the run stops and asks, a red CI included. The rounds are counted across restarts; a restart after a stop the limit did not cause (a killed stage, a restarted container) gets one more, recorded with its reason. A check that did not finish, killed or superseded by a newer commit, costs no round: it runs detached from the checker, which rejoins it at the same commit, and the workflow starts it again, at most twice in a row, naming the stage and its log.
9. The contributor archives the OpenSpec change, commits the planner's queue and the history rows of the changes merged before it, commits the title and the gated body as the archived change's `pr.md` (`tools/open_pr.sh write`), and pushes the branch once; the push of a `feature/`, `bugfix/`, `hotfix/`, `release/`, or `chore/` branch runs `.github/workflows/branch-push.yml`, which holds no permissions and runs no repository code, and its completion runs `.github/workflows/open-pr.yml` from main, which reads the branch's new `pr.md` as data, gates it with main's tools, opens the pull request on GitHub's runners with the `AI` environment's `PR_TOKEN` (the environment allows main alone as a deployment ref, so no branch's code runs beside the token), and reads it back equal; a branch without a new `pr.md` or with an open pull request is left alone, and no step pushes a tag or deletes a ref. `tools/open_pr.sh wait` records the number. No agent creates a pull request with a tool or GitHub's API, since one created or edited from a cloud session gets a footer its network layer appends; a pull request opened by hand before the push gets its text through the session's update tool, which arrives clean. The merger waits for CI, which compares the pull request's measurements with the last push to `main`, without giving up while a check still runs: one merger start waits up to 30 minutes, in the foreground through `tools/ci_wait.sh`, 3, 4, then 5 minutes at a time; a red run goes back to the contributor with its log. A merge whose CI passes within two waits takes at most 12 tool calls: the workflow hands the merger its records and the merge gates as one command. On green the merger fetches main by its own refspec and runs the merge gates of a fresh worktree of `main`, which the branch cannot have edited, and squash-merges the head they checked with the body the contributor wrote, passing the full sha the push recorded as the head GitHub must find. The merge tool has its own hook: `main`'s guard refuses a merge that is not a squash at the head the push recorded and the merge gates passed at, or while `origin/main` differs from origin's `main`.
10. The retrospective closes the run in one start: it runs the run's last records, flags a run over its size budget with a line starting `under:` or `over:` (the run state keeps the size the planner estimated, so the history row carries it beside the total and output tokens after the queue item is gone), and proposes at most three ways to simplify the workflow, its script, or its agents, each backed by numbers, and writes the report in a fixed shape that names any rule broken. The delivery never reviews the whole codebase itself; its report says when the sprint's fifth change has merged.
11. Sprint planning closes each sprint of five merged changes: the main session starts `/sprint` (`.claude/workflows/sprint-planning.js`) after every merge, and it ends at once, with the line of `tools/run_state.sh review-due`, until the sprint is due. Then the security reviewer, never skipped, and the quality reviewer review the sprint's combined diff, the quality reviewer taking the broad points the per-change review only notes: style, naming, the layers, duplication across the changes, and docs currency. A skeptic reads both results against the code: a quality finding it drops is never recorded, and a security finding it disputes is recorded as disputed, never dropped. Every second sprint the whole-tree review of `/review` runs beside them. The planner, in its sprint mode the only reader of the backlog, then grooms it, duplicates found by `backlog-dups` and decided by the model, entries removed by the headings a merged item listed, a security entry leaving only that way or with the commit that fixed it named, and writes the next sprint of 5. Its files wait in `build/plan/` until the next package step runs `tools/run_state.sh groom`, which applies a plan once (it retires the plan's marker, and a sprint whose row stands is not applied again), checks every removal, writes nothing if one fails, applies the queue, and adds the sprint's row to `docs/sprints.tsv`: its merges, wall minutes per change against the pace of one an hour, total tokens and the runs over their budgets, and first passes. A brief that excludes the planning records sets `records=skip` in its change's run state, and that package step runs neither `groom` nor `history`. A review that reaches its cap returns what it covered and is recorded as `partial`, and one that returns nothing as `not-run`, never as passed.

Rules are checked, not remembered. `tools/gates.sh` refuses a commit without its single co-author trailer, a link, an email address, a session id, or a model name in the diff, the commits, or the pull request; a snapshot not written by the test runner; a new file missing from the code map; a new command, binding, option, make target, or process change without this README; a spec change that leaves this README or `docs/architecture.md` as they were, or a process change that leaves `CLAUDE.md`, unless the change's proposal says why; an added or modified spec scenario that no test names; a second push without a CI failure to fix; and a merge without the recorded passes of the check, the quality and security reviews, and the benchmark at the pushed head. One scanner, `tools/scan_text.sh`, reads the forbidden text for every check: the gates at the push and the merge, and the `scan` workflow on each pull request, which runs the base commit's scanner, so a pull request cannot weaken its own check, and reads its title, body, commit messages, and added lines whenever it is opened, edited, reopened, or pushed to, so a footer added to the body after it opens turns the check red and the merger, which merges only over green checks, waits until it is removed. No local commit hook is installed: the gates and the agent guard refuse any `core.hooksPath` and any hook but a sample in `.git/hooks`, since a hook a checkout can write would run code of any branch.

Documents are budgeted too. `make docs-lint`, a stage of `make check`, keeps `CLAUDE.md` within 30 KiB, each agent file within 8 KiB, `docs/architecture.md` within its budget, and `docs/queue.md` within 17,369 bytes, because agents read them on every run, and refuses a link, an address, a model name, hard-wrapped pull request text, or a path that no longer exists. When `authoring-kit` introduced it, `CLAUDE.md` went from 41,066 to about 30,600 bytes and `docs/architecture.md` from 91,890 to about 87,300, the detail moving to `docs/spinel-notes.md` and `docs/examples.md`.

The run state of a change, `build/pipeline/<change>.json`, records each phase and the commit it finished at, every check stage, the reviews, the pushes, the pull request, and CI. It is written only by `tools/run_state.sh`, which refuses a control character in any key or value, so an interrupted run picks up where it stopped, trusting only the records at a commit of the branch or of `main`; on a resume the check, the reviews, and the benchmark run again, since branch code run by the checks could have written a pass, past the push included, and only the verdicts a start received reach the merge gates' records. A fix round narrows a review to the commits since a pass of the same start, never one only the run state holds, and every High or Medium security finding at confidence 8 or above in the change blocks, a re-rating of an earlier non-blocking one included. The phases and the reviews are recorded by the workflow from what each agent returned, never by the agents, and the merger compares them with what the workflow received before it merges. Every agent runs `main`'s `tools/agent_guard.sh` before each shell command or file write, and a guard that is missing or fails refuses the call; it refuses every call while `.git/config` sets a key that runs a command or redirects origin, which the push and merge gates refuse too, with an `origin/main` other than origin's `main`. Each agent may run only the commands its role needs, read as the shell reads them: the agents that never edit cannot commit, push, call `gh`, write the run state's records, or write a file outside their own directory, and the contributor pushes only through `tools/run_state.sh push`, which runs the gates first. Until that push the commits stay on the local branch, and a run pushes once, plus once per CI fix: findings that arrive after the package step are recorded in the run state and committed by the next change's package step with the metrics row. The checker runs the fast stages (`FAST_STAGES`) and CI the rest on the pull request; a red CI superseded by a green run of the same check, or one only on the scan of the pull request body, costs no fix round.

Every run is measured. `/deliver` records the total tokens and wall minutes of each start, which only the session that ran the workflow sees, with `tools/run_state.sh usage`; the workflow counts the output tokens and tool calls of each phase, whether each gate passed the first time, the rework rounds, and the CI minutes, and stores them in the run state: each metric line holds every figure, run by the workflow's record step after the reviews and at the end and by the merger and the retrospective before their work, so a resumed run keeps them and the run state's totals equal the ones the retrospective is given; the check adds allocations and time per key and the analysis rounds. `/deliver` also records each agent start's input, cache, and output tokens from the Workflow run's transcripts, weighted by its tier's price, per start and per phase (`tools/run_state.sh tokens`), and the closing start the seconds of each CI step (`tools/run_state.sh ci-stages`), beside the merger's calls waiting on CI, in the history's last four columns; later cost changes are judged on the weighted figure. Each agent start is told its cap of tool calls, a figure per kind of start scaled by the size estimate (a fixed one for the starts of sprint planning and the periodic review), and a start that reports more is recorded for the planner; each agent file's `maxTurns` is the ceiling the platform enforces. Each kind of start runs on the model tier and reasoning effort of the workflow's calibration table, recorded beside its figures and in the history's `calibration` column; the table moves one kind at a time by the rule of `docs/goals.md`, and never the security reviewer. A contributor or reviewer stopped by its cap returns what it left, and one stopped by the ceiling returns nothing; either is continued by another start told what is left, at most twice in a row, so the run resumes from the committed work instead of failing. `docs/metrics.tsv` keeps one row per merged change, written only by `tools/run_state.sh`, and `/status` prints the last row and each gate's first-pass rate.

To start or resume a change, run `/deliver` followed by a change name or a short description in Claude Code; `/status` shows the running change and its next phase, `/plan` asks the planner for the next order of the queue with its evidence, `/sprint` closes a sprint once its five changes merged, and `/review` runs the whole-tree review now. Outside Claude Code the same checks run with `make check`, `make gates`, `make metrics`, and `sh tools/run_state.sh status`. The plan lives in the repository: `docs/goals.md` is the charter every change serves, the UI first, then code intelligence, security never traded for either, `docs/queue.md` the ordered queue with the reason for each place and the user's standing decisions, and `docs/metrics.tsv` the data behind it. Main-session notes do not survive a reset, so everything a later session needs is in these files: when the project is put on hold, the queue says so in its header, and work resumes with `/status`, which shows the queue and any unfinished run, then `/deliver` with the first item's name.
