# carat

A terminal IDE written in Ruby with Neovim's modal editing model, built, tested, and shipped with Spinel. `docs/architecture.md` holds the design and the roadmap; `docs/design.md` is the binding look (the Facet rules, colors, and glyphs); `docs/codebase-map.md` places every source file in its area; `CLAUDE.md` holds the commands and conventions.

Today it is an editor with split windows, tab pages, a plugin host, a file tree, and a fuzzy file finder: normal, insert, operator-pending, command-line, and the charwise, linewise, and blockwise visual modes (`v V <C-v>`, `o O gv`, every motion and text object, and `d x y c s > < J gJ p P r ~ u U X D C S R Y I A gc` on the selection); counts, the `"x` register prefix, and Neovim's `[count] operator [count] motion` grammar; the motions `h l 0 ^ $ f F t T ; , j k G gg + - _ w W b B e E ge gE ( ) { } H M L`; search with `/ ? n N * # g* g#`, also under an operator and in the visual modes; substitute with `:s`, `:&`, `&`, `g&`, and the ranges `% . $ N '<,'>`; the global commands `:g`, `:g!`, and `:v`, and the line commands `:d`, `:m`, `:co`, `:t`, `:j`, `:>`, `:<`, `:normal`, and `:p`; the text objects `iw aw iW aW is as ip ap` and the bracket and quote objects; the operators `d c y > < g~ gu gU` with `dd cc yy >> << g~~ guu gUU` and `x s S C D Y J p P r ~`; Neovim's commenting with `gc{motion}`, `gcc`, visual `gc`, and the `gc` text object (`dgc`), by the marker of the filetype (`#` for Ruby and for any filetype without its own row); undo and redo with branches (`u`, `<C-r>`, `U`, `g-`, `g+`, `:undo`, `:redo`, `:undolist`, `:earlier`, `:later`) and the dot command `.`; the unnamed, named, numbered, small delete, black hole, and read-only registers with `:registers`; insert-mode editing; the window commands `<C-w>s v h j k l w W p c o = q`, also with Ctrl held on `s v h j k l w p o q`, which wait for their second key however long it takes; `gt` and `gT` over the buffer tabs of the top row (`option.gt tabpages` gives them Vim's tab pages back), whose tab `:q` on the last window closes while another buffer tab is left and `:bd` closes keeping every window, the empty startup buffer leaving the row once a file opens in another window or tab page, from the explorer moving the file window's buffer tab, as `:bn` and `:bp` do, while in a reading view they switch that window, which is no side window, and the explorer's `t` opens a buffer tab there, `<C-PageDown>`, `<C-PageUp>`, and `g<Tab>` over the tab pages, and `[b ]b [B ]B` over the buffers; scrolling with `<C-f> <C-b> <PageDown> <PageUp> <C-d> <C-u> <C-e> <C-y> zt zz zb` and the `scroll` option; manual folds per window with `zf zo zc za zd zE zR zM` and the fold motions `zj zk [z ]z`, nested as Neovim nests them, a closed fold drawn as one dim row in the `Folded` group, passed by `j` and `k` as one line, and taken whole by a linewise operator such as `dd`, opened by insert and replace mode, and dropped with a closed window; and the ex commands `:w :q :wq :x :wa :qa :wqa :xa :e :sp :vs :new :vnew :close :only`, the buffer list commands `:ls :buffers :files :bnext :bprevious :bNext :bfirst :brewind :blast :buffer N :bdelete`, and `:tabnew :tabedit :tabclose :tabonly :tabnext :tabprevious :tabfirst :tablast`, with a tab page number for `:tabclose :tabonly :tabnext :tabprevious`. Ruby files are highlighted in color, and `:syntax on`, `:syntax off`, `:set filetype=`, and `:set syntax=` switch it. `:e` refuses a directory, a FIFO, a device, a symbolic link whose target is missing, or a file over 64 MiB with Vim's message and keeps the current buffer. A file that is not valid UTF-8 opens with its bytes kept and written back as they were, `[ILLEGAL BYTE in line N]` naming its first such line and each illegal byte drawn as one U+FFFD cell. Compiled plugins add actions, ex commands, side windows, floating windows, and tokenizers through the API in `docs/plugins.md`; Escape in normal mode closes the topmost floating window, and `:q` or `<C-w>c` in a focused one closes it; the built-in `explorer` plugin, the file tree below, and the built-in `ruby` plugin, the Ruby tokenizer, and the built-in `git_signs` plugin, which shows the git branch with its ahead and behind counts in the status bar (`± main ↑1 ↓2`) and a sign on each line added, changed, or deleted since HEAD (`┃`, `┇`, `▁`), a window focus with HEAD unchanged running no git and a git command past its deadline running none until HEAD moves, when Carat runs in a directory under a root of `language.trusted_roots` (elsewhere it runs no git, since a cloned repository's configuration can name a command, and even there git runs with lazy fetching, the `ext::` transport, and the fsmonitor hook off), are built on it. `docs/compatibility.md` lists every Neovim command it implements with its test, and `docs/backlog/` the known items left for later changes.

## Building

The prerequisites are a C compiler, `make`, `git`, and `curl`. No Ruby interpreter is needed, not even to build the compiler, and none is ever used: every `make` target puts `tools/noruby` first on its `PATH`, whose `ruby` refuses to run, so a CRuby installed on the machine is never reached.

1. `make toolchain` fetches the pinned Spinel commit into `tmp/.spinel`, builds it, and installs `spinel`, `spin`, and `spinel-doctor` under `tmp/.toolchain`. Both directories are ignored by git, every `make` target finds the toolchain there on its own, and `make toolchain-clean` removes them.
2. `make build` compiles the editor to `build/bin/carat` and prints the alias line to add to your shell profile to run it from anywhere; `make install` puts it on the `PATH` instead.
3. `make check` runs the canonical stage list: the toolchain check, the documents' size and quality, the release and development builds, the generated config's freshness, every test against its snapshot, `spinel-doctor`, the `make no-cruby` proof, the allocation budget, the tests of the shell tools, and the rule gates; run it before every push. `make test-one T=test/NAME.rb` compiles and runs one test on its own. Run tests, snapshots, and benchmarks only through `make`, never with `spin test` directly: for a test program without a snapshot, `spin test` compares against the `ruby` on your `PATH`.

## Starting

`carat FILE` opens a file, or starts a new one when nothing is there. `carat` with no argument, or with a directory, starts on an empty buffer and shows the start screen: a gem forms from a point in about 0.6 seconds, a sparkle lights its top, and `c a r a t` appears with the keys to insert text, open a file, and quit. Any key ends it and does what it always does. `option.startscreen false` turns it off, `option.reducedmotion true` shows the finished picture without the animation, a terminal too small for the gem shows only the wordmark, and with the `NO_COLOR` environment variable set the picture is drawn in plain ASCII without colors of its own.

The cursor is a block in normal mode, a bar in insert mode and on the command line, and an underline in replace mode, and the current window highlights the cursor's line, its gutter included (`option.cursorline false` or `:set nocul` turns it off). However carat ends, `:q`, a signal, or an error, the terminal gets its own cursor shape and its main screen back.

## Leader keys

The leader is Space. Its keys come in groups named by their first letter, and each group key waits for the next key however long it takes; Escape cancels it.

- `<leader>w` windows: `ws` split, `wv` split vertically, `wh` `wj` `wk` `wl` go to the window left, below, above, or right, `wc` close, `wo` keep only this one; a count works as with `<C-w>`.
- `<leader>q` quit: `qq` quits as `:qa` does, `qw` writes every changed buffer and quits as `:wqa` does.
- `<leader>f` files: `fs` saves as `:w` does; `ff`, like `<C-p>`, opens the file finder: type to filter the project's files, by a substring of the path or by initials (`ep` finds `explorer_plugin`, `fgr` finds `finder/grep.rb`: up to four runs of letters, each after the first at the start of a path segment or word), several words in any order, case ignored, a substring above initials and a file name above a directory, and letters scattered through a word match nothing, `<C-n>` and `<C-p>` move the highlighted row (a sapphire `▎` on the selection color with its path in bold), `<CR>` opens (with no match it keeps the finder open on what you typed, so a typo costs only its correction), `<C-x>`, `<C-v>`, and `<C-t>` open in a split, a vertical split, or a tab (a buffer tab under `option.gt buffers`, a tab page under `option.gt tabpages`), `<Esc>` closes, and a terminal of 100 columns or more previews the highlighted file in a box beside the list, the two sharing an edge under every `winborder`; `fg` opens the same picker over file contents: the project's files are read once when it opens, typing lists the lines that hold every typed word as a substring, in any order (words split at spaces, case ignored, whole-word hits first, then lines with more hits, each matching file's best line before any file's second, at most 200 rows, the title counting the files and lines that match as `Grep 149 of 149 files, 586 of 148091 lines`), each as path, line number, and text, and the same keys open the pick at its line and column (every line of a file of at most 256 KiB is searched, a binary file is skipped, a line is cut at 400 bytes, up to 400,000 lines are stored with the title marking a larger tree, a key checks at most 30,000 new lines, checking the last key's matches again and continuing where it stopped while the typed words only grow, with `+` on the counts while lines remain unchecked, bidirectional marks, zero-width characters, and line separators show as spaces, a terminal of 100 columns or more previews the highlighted row's file beside the list from the text already read, its matched line in the middle and marked, down to the file's last line, safely shown); `fb` opens the same picker over the open buffers, in `:ls` order, `fr` over the files you opened, most recent first, also after `:bd` and after Carat restarted (the list is written as absolute paths to `~/.local/state/carat/recent_files` when Carat ends and read when it starts, a missing or unreadable file or a line that is not a usable path read as empty, never an error, and a file outside the working directory is listed by its absolute path), at most 100, and `fR` opens the last picker you closed again, with what you typed and the highlight where you left it; `fw` opens the grep picker on the word under the cursor (the empty prompt on a blank), and `<C-g>` in any picker switches between the file picker and the grep picker, keeping what you typed.
- `<leader>b` buffers: `bb` lists them as `:ls` does, `bn` and `bp` go to the next and previous one, `bd` deletes this one, or with a count the buffer of that number.
- `<leader>d` docs: `dp` pins the documentation float `K` opened into a split, `dd` peeks at the definition under the cursor in a float.
- `<leader>l` layout: `ls` hides the left sidebar and shows it again where it was, `lr` does the same for the right sidebar and `lp` for the bottom panel.
- `<leader>e` opens the file tree, as before.
- `<leader>p` (or F1) opens the command palette: every action and ex command, each row its description first, then its dotted name, dimmed, and its key on the right (a control key as `^W`), a text too long for its column cut with `…` (`>` under `option.icons ascii`) and the name left out on a narrow screen, the key too on the narrowest, so a row always shows its description, filtered as you type with the typed letters marked; Ctrl-N and Ctrl-P move the selection, Enter runs it, Escape closes it.

Pause after a group key, or after `g`, `z`, or `<C-w>`, and a panel centered at the bottom lists the keys that may follow and what each does, a group of your own named by the actions under it. `option.keyhints.delay` sets the pause in milliseconds (300; 0 turns the hints off), and `keymap.group <keys> <name>` names a group of your own, as `keymap.group <leader>w panes`.

Ctrl-S saves in normal and in insert mode, where you stay in insert mode.

In insert mode a completion popup lists the names the language server offers for the word before the cursor, matched fuzzily (`fn_na` finds `file_name`), each with its kind's icon and its type on the right: Ctrl-N and Down select the next, Ctrl-P and Up the previous, Enter inserts the item over what you typed, Tab replaces the whole word, and Esc closes the popup. The names come from the file type's language server when it offers completion: Carat asks it once you pause for a tenth of a second, without making a key wait, cancels a question about a word you have left, and fills the popup when the answer arrives. Without a language server, or before it answers, Ctrl-N and Ctrl-P complete the word before the cursor from the words of the open buffers, as in Neovim: Ctrl-N scans forward from the cursor through the current buffer and then the other buffers, Ctrl-P backward, and the words show in the same popup with the nearest selected, or `Pattern not found` when none matches. The selected name's documentation shows beside the popup, from the answer or asked for once the selection rests on it for a tenth of a second, once per name. In normal mode `K` asks the language server for the documentation under the cursor and shows it in a bordered float when the answer arrives; `K` again enters the float so the usual keys scroll it, `Esc` or moving the cursor closes it, and `<leader>dp` keeps it in a split. Both floats and the split draw the documentation with its headings, emphasis, code spans, links, and fenced code styled, the code highlighted like a buffer of its language when a plugin tokenizes the language the fence names (unless `:syntax off`), and plain with `NO_COLOR` set. In a Markdown file (`.md` or `.markdown`) `<leader>dr` shows it as reading text in the same window, at most 80 columns wide, its headings, emphasis, code, and links styled the same way, lists as bullets and quotes as bars, the lines of a paragraph or a quote flowed into one text wrapped at the measure (a line ending in two spaces keeps its break) with a quote's bars and a list item's indent on every wrapped row, tables drawn in aligned bordered columns whose cells wrap to fit, fenced code drawn in a frame, and `<leader>dr` again shows the file with the cursor where you left it; very large files are read up to 256 KiB. Carat runs the terminal in raw mode, so flow control is off and Ctrl-S reaches it instead of freezing the screen. In normal mode `gd` asks the language server for the definition under the cursor and goes there when the answer arrives, opening its file; Ctrl-O goes back to where you were and Ctrl-I (Tab) forward again, through every position `gd`, a jump motion (`G`, `gg`, `%`, `{`, `}`, `H`, `L`, a search, `n`, `:N`), or a switch to another file (`:e`, `:b`, `:bn`, the finder, the explorer) left, each window keeping its own list as in Neovim, and Ctrl-^ or `:e #` shows the file the window showed before. Several definitions show a short list to pick from with Enter, a definition outside the project opens read-only, which no write takes, a jump to a file with no tab takes over the tab of the file you leave so the tab row does not fill up (`option.jumptab keep` keeps both, as Vim; the file left stays loaded, shown by `:ls!` and reached again with Ctrl-O or `:b N`), and with no server offering definitions or no answer you get Neovim's message. Typing `(` or `,` inside a call asks the language server for its signature, shown in a small float above the cursor with the argument you are at highlighted; it follows the cursor from argument to argument and closes when you leave the call or press Esc.

These keys moved: `<leader>w` used to write the file and `<leader>q` to quit the window. Press `<leader>fs` or Ctrl-S to write, and `:q` or `<C-w>q` to close a window, or `<leader>qq` to quit. To get the old keys back, add `keymap.normal <leader>w :w<CR>` and `keymap.normal <leader>q :q<CR>` to `~/.config/carat/caratrc`.

## Configuration

Carat reads its settings from plain text files of one setting per line, `scope.name value`: the first word is a dotted key, and the rest of the line is the value, a word, a number, `true` or `false`, or a list of words separated by spaces. A word containing spaces goes in double quotes (`\"` and `\\` inside them stand for a quote and a backslash), `#` starts a comment, and blank lines are ignored.

```
# ~/.config/carat/caratrc
option.number true
option.tabstop 2
option.theme carat-dark
keymap.normal <leader>e plugin.explorer.toggle
keymap.normal <leader>w :w<CR>
keymap.normal Q none
plugin.explorer.enabled true
plugin.explorer.width 30
plugin.explorer.ignore .git build tmp
plugin.finder.ignore .git build tmp node_modules
```

- `option.<name>` sets an option by its Vim name (`number`, `relativenumber`, `tabstop`, `shiftwidth`, `expandtab`, `autoindent`, `scroll`, `scrolloff`, `timeoutlen`, `undolevels`, `cursorline`, and the others), plus Carat's `icons`, `theme`, `background`, `startscreen`, `reducedmotion`, `breadcrumbs` (`auto`, `always`, or `never`), `jumptab` (`replace` as shipped or `keep`), `showtabline` (Neovim's 0, 1, or 2: the tab row never shows, shows only with two or more tab pages or files, or, as shipped, always), `winborder` (the border of floats, Neovim's `none`, `single`, `double`, `rounded` as shipped, or `solid`, drawn with `+`, `-`, and `|` under `option.icons ascii`; every float has a column of padding on each side and its title centered on the top edge, as a notification's severity is, a float placed from the screen's corner keeps one cell from its edges and bars, the palette is centered again after a resize, and a float's text is never wider than the screen less its margin, padding, and border, so no row is cut), `indentguides` and `indentguides.char` (the indent guides of file windows, on with `┊` as shipped, the cursor's block a solid `│`, both `|` with `option.icons ascii`), Neovim's `hidden` (on as shipped: `:e` and the buffer commands leave a modified buffer hidden instead of refusing it with `E37`, `false` keeps the refusal) and `list` and `listchars` (the marks of tabs, trailing spaces, and no-break spaces in file windows, off as shipped, `tab:→ ,trail:·,nbsp:␣` drawn in the indent guides' quiet color, Neovim's `>`, `-`, and `+` with `option.icons ascii`), and the slot sizes `layout.left_width`, `layout.right_width`, and `layout.panel_height` (0, the default, keeps the size a view asks for); `tabstop` takes 1 to 9999 and `shiftwidth` 0 to 9999, as in Vim, `scroll` and `scrolloff` 0 to 9999 lines, and `timeoutlen` and `undolevels` 0 to 10000. `:set` changes all of these but `jumptab`, `gt`, `keyhints.delay`, `indentguides`, and the slot sizes while the editor runs, with Vim's forms and the same checks: `:set nonu`, `:set invlist`, `:set ts=4`, `:set sw+=2`, `:set lcs=tab:>-`, `:set winborder?`, `:set ts&` for the shipped value, a bare `:set` for the options you changed, and `:set all` for every one; `startscreen` is read only at startup.
- `keymap.<mode> <keys> <action>` binds keys in Vim notation in `normal`, `insert`, `visual`, `visual_line`, `visual_block`, `operator_pending`, or `cmdline` mode, or in the `completion` layer that answers first while the completion popup shows, to an action from `docs/actions.md` or to keys to replay, such as `:w<CR>`; the action `none` removes a binding. `keymap.pick <keys> <action>` binds in a pick list instead, as the definition pick list's `keymap.pick <CR> definition.choose`. `keymap.leader <Space>` sets what `<leader>` stands for.
- `plugin.<name>.enabled` turns a plugin on or off, and `plugin.<name>.<option>` sets one of its options.
- `language.<name>.lsp` names the command a language server runs, and `language.<name>.lsp.root ROOT COMMAND...` the one run instead when Carat runs in ROOT or under it, such as `language.ruby.lsp.root ~/work docker compose exec app ruby-lsp`, its words run as written with no shell, the later covering line winning, a ROOT that is not absolute or under `~`, or that holds a `.` or `..` segment, reported (a `language.<name>.formatter` line is reported as not supported yet, since formatting has not landed): opening a file of a language whose `lsp` command is installed starts that server when Carat runs in a directory under a root of `language.trusted_roots` (for example `language.trusted_roots ~/src`, set in the user file, none by default), since a server such as ruby-lsp runs the project's own code; anywhere else the status bar reads `untrusted :LspStart` and `:LspStart` starts it. The bar shows the server's name and state (starting, indexing with a percent, stopped, or crashed, which `:LspRestart` restarts); quitting and `:LspRestart` end the server process Carat started, and no other, and the server is told about the open files. Its diagnostics show as signs in a one-cell column before the line numbers, the cursor line's message in the bottom row in normal mode, and the counts of errors, warnings, infos, and hints on the bar. A server's messages show as notifications at the top right, at most three, leaving after 3, 5, or 8 seconds by severity, and its long work (indexing) as a title and a progress bar on the status bar, which stays still with `option.reducedmotion true`; with `NO_COLOR` set both are drawn in ASCII without color. `:messages` shows the messages and notifications shown so far, and `:messages clear` forgets them. They are read from the defaults and the user file only, never from a project's file, so opening a directory cannot choose a program to run. For the same reason a project's file may bind keys only to `none` and to the actions that move, edit, select, search, scroll, fold, complete, or switch buffers, tabs, and windows (the families of `Config::PROJECT_BINDABLE`), not to keys to replay, an action that writes or quits (`file.save`, `quit.*`, `window.quit`), the command line's own actions (`cmdline.*`), or any plugin's action, such as the explorer's delete, in any mode, nor, in insert, replace, or command-line mode or the completion popup, any action but one that edits, moves by arrow, scrolls a page, or completes there (`Config::TEXT_BINDABLE`), so insert-mode `<CR>` cannot leave insert mode and turn the next letters typed into commands, nor `mode.cmdline` or `palette.open` outside the normal and visual modes or on keys typed while editing text, letters, arrows, and the other editing keys, such as `;`, `<Space>x`, or `<Up>` (`<F4>`, `<C-k>p`, or `<M-p>` work); it may not unbind or rebind a key the defaults or your file bind to one of those, to `:` for the command line, or to `<Esc>` that leaves insert mode or the completion popup, so `keymap.normal : none` there is reported and `:` still works, nor bind keys that start with such a key or begin one, such as `:w`; and it may not set `keymap.leader`, which would move the `<leader>` write and quit bindings onto keys such as `d`.

The files load in order, and a later line wins: the built-in defaults (`config/default.caratrc`, every option and binding Carat ships, built into the binary), then `~/.config/carat/caratrc`, then `.caratrc` in the directory Carat starts in. Every line is checked when the files load; a mistake is reported as `file:line: message`, that line is skipped and the rest still applies, and the first problem shows in the message row when Carat starts, with the number of the others. A line holding a byte that is not UTF-8 is such a mistake. A configuration file that is not a regular file (a FIFO, a device) or holds more than 1 MiB, and a project's `.caratrc` that is a symbolic link, also when it becomes one between the check and the open, is reported and not read, so a cloned repository cannot hang or exhaust Carat at startup.

## Command line

`:` opens the command line, `/` and `?` the search prompts, and the command palette and the finder their `> ` prompt, drawn on the first row of their float with the cursor in it; all of them keep a cursor, drawn as a bar, and are edited as Neovim's command line is. `<Left>` and `<Right>` move by character, `<Home>` and `<C-b>` to the start, `<End>` and `<C-e>` to the end, `<S-Left>` and `<C-Left>`, and `<S-Right>` and `<C-Right>`, by blank-separated word; typed text goes in at the cursor, `<BS>` removes the character before it and `<Del>` the one under it, `<C-w>` the word before it and `<C-u>` everything before it, and `<Up>` and `<Down>` recall the history with the cursor at the end of the line. A `<BS>` on an empty line leaves the command line. At the `:` prompt `<Tab>` completes a command name, a palette name after `:colorscheme`, or a path after `:e`, `:w`, `:sp`, `:vs`, and `:tabe` (relative to the working directory, or as typed from `/`, `../`, or `~/`, a directory ending in `/`, at most 1000 entries read per directory), and lists the matches in a popup above the line; `<Tab>` and `<S-Tab>` step through them and back to the typed text, typing goes on from the match, and `<Esc>` closes the popup before it discards the line. `<C-r>` register insert and the `wildmode` and `wildoptions` options are not there yet; `docs/compatibility.md` lists the differences.

## Search

`/pattern<CR>` searches forward and `?pattern<CR>` backward, `n` and `N` repeat the last search in the same or the other direction, and `*`, `#`, `g*`, and `g#` search for the word under the cursor. Each takes a count, works after an operator (`d/foo<CR>`, `cn`) and in the visual modes, wraps around the buffer with Vim's "search hit BOTTOM, continuing at TOP", and the last pattern is in the `/` register. `<Up>` and `<Down>` at the `/` or `:` prompt recall earlier patterns or commands starting with what you typed.

- Patterns are Vim's magic patterns: `. * \+ \= \{n,m} ^ $ [a-z] \( \) \| \< \> \s \d \w \k \c \C \v \V` and the rest `docs/compatibility.md` lists, with `~` for the last substitute's replacement string; back references and look-around are not supported.
- `hlsearch` (on) highlights every match until `:noh`, the match under the cursor bold in a stronger color as Neovim's `CurSearch`, `incsearch` (on) moves to the first match while you type, and `ignorecase` with `smartcase` ignores case unless the pattern has a capital letter; set them with `option.hlsearch false` in a configuration file or `:set nohls`, `:set ic`, `:set scs?`. The bracket under the cursor and its partner, when the partner is in view, are painted in `MatchParen` (not in insert mode).
- A pattern can never hang Carat: one too large is refused with `E363`, and a search that would scan too long stops with a message.

## Substitute

`:s/pattern/string/` replaces the first match on the cursor line, and `g` after it every match: `:%s/old/new/g` changes every line, `:2,5s/a/b/` lines 2 to 5, and `:` in a visual mode starts the command line with `'<,'>`, the selected lines. A range alone moves the cursor (`:12`, `:$`). The string takes `&` for the match, `\1` to `\9` for the pattern's `\(\)` groups, `~` for the last string, `\u \U \l \L \e` for case, and `\r` for a line break.

- The flags `& e g i I n r p #` work as in Vim: `:%s/x//gn` counts the matches, `e` keeps quiet when there is none, `i` and `I` set the case of that substitute alone, `n` then searching by the options, and `&&` reuses the last flags; `c` and `l` answer Not implemented and leave the last substitute as it was.
- `:&`, `:s` alone, and `&` repeat the last substitute on the range or the cursor line, `3&` on three lines, and `g&` on every line with the last search pattern and flags.
- A substitute is one undo step, its pattern becomes the last search for `n`, and like a search it can never hang Carat: one that would work too long changes nothing and reports `E363`.

## Global

`:g/pattern/command` runs an ex command on every line that matches: `:g/TODO/d` deletes those lines, `:g/^#/s/x/y/` substitutes on the comment lines, `:g/x/m0` moves those lines to the top in reverse order, and `:g/x` alone lists them. `:v/pattern/command` and `:g!` run on the lines that do not match. A range limits the lines (`:10,20g/x/d`); without one every line counts.

- A line is visited only if it matched before the command ran on any line, so lines a command deletes or inserts are never visited by mistake.
- `:[range]d [x] [count]` deletes lines into a register, the numbered registers shifting as with `dd`.
- A global is one undo step, its pattern becomes the last search for `n`, and like a search it can never hang Carat.

## Syntax highlighting

Carat highlights the files whose filetype a plugin tokenizes; the built-in `ruby` plugin covers Ruby: `.rb`, `.rake`, `.gemspec`, and `.ru` files, `Gemfile`, `Rakefile`, `config.ru`, and any file whose first line is a `ruby` shebang. Comments and their `TODO`s, keywords, definitions, constants, variables, symbols, numbers, strings with escapes and nested interpolation, percent literals, heredocs, and regular expressions get Neovim's standard highlight groups, and a construct that spans lines keeps its color on the lines that follow. Only the rows on the screen and the rows above them are ever tokenized, so a large file opens as fast as a plain one, and an edit re-highlights only until the colors after it are the same as before.

- `:syntax off` draws every buffer plain and `:syntax on` brings the colors back.
- `:set filetype=ruby` (or `:set ft=ruby`) highlights the current buffer as Ruby, `:set syntax=OFF` turns one buffer plain, and `:set ft?` shows the filetype.

The colors come from a palette, chosen by the `option.theme` line of the configuration: Carat's own `carat-dark`, the default, and `carat-light`, with a sapphire accent, or the other editors' `one_dark` and `dark_plus` (Visual Studio Code's Dark+) for a dark terminal and `one_light` and `light_plus` for a light one. `:colorscheme one_dark` (`:colo`, `<Tab>` completing the names) or `:set theme=one_dark` switches the palette while the editor runs, every color drawn again at once, `:colorscheme` alone shows its name, and `:set bg=terminal` switches the background. Each palette has its own syntax colors and colors the status bar and its mode pill, the file name and the position leading in bold while the branch, the file type, the encoding, and a server with no state step back in a quiet color of the bar's own that reads at 4.5:1 at every color depth, the groups of the bar three cells apart, the language server's segment and the diagnostics counts drawn on the bar's own background and readable there at 16 colors too, the buffer tabs, the line numbers, the selection, the search matches, the messages, and the file tree's icons as well, and every text color in it is readable on its background and on the cursor line at WCAG AA contrast. Carat's two palettes frame floats in a border color of their own that stays out of the text's way, draw the search matches on a soft tint, and keep their panels apart from the background at 256 colors; the command line's mode pill is cyan in every palette. Each sign takes its kind's color: an error red, a warning yellow, and git's added, changed, and deleted lines green, cyan, and red. By default the palette paints its own background under every cell, the cleared screen included, which needs a terminal that clears with the current background color, as most do; `option.background terminal` keeps the terminal's own background instead. In the bottom row an error shows an icon, its code in bold red, and its text, any other message, the visual mode indicator, and the command line's prompt and pending keys are dim, and insert mode leaves the row blank, since the status bar's pill shows the mode.

```
option.theme light_plus
option.background terminal
```

Carat writes 24-bit colors when the terminal sets `COLORTERM` to `truecolor` or `24bit` (most modern terminals do), the 256-color palette otherwise, and the 16 basic colors when `TERM` names a terminal that has only those, such as the Linux console (`linux`). To turn the Ruby highlighting off, add the line `plugin.ruby.enabled false`.

## File tree

Each tab page has a left and a right sidebar and a bottom panel. A plugin's view opens in one of them, under a header row naming the views opened there; a sidebar is drawn on a darker background than the editor and no separator glyph stands where it meets the editor (the glyph stays under NO_COLOR and at 16 colors, where the backgrounds do not show the edge), while two editor windows side by side keep their `│` line; a sidebar keeps its width and the panel its height when windows are equalized, and `<leader>ls`, `<leader>lr`, and `<leader>lp` hide and show them.

With two or more file windows each shows a winbar on its first row: its file's path and, when the language server offers document symbols, the class and method the cursor is in, as `a.rb › Foo › bar` (`a.rb > Foo > bar` under `option.icons ascii`), the path and the outer names dimmed and the innermost name, or the path when there is none, on the accent the selected buffer tab shares in the current window. `option.breadcrumbs always` shows it on a single window too and `never` turns it off. The selected buffer tab reads by its accent background and bold, with no gem. Every tab ends in a thin `│` (`|`).

`<leader>e` (Space, then `e`) or `:Explorer` opens a file tree in the left sidebar, 30 columns wide, rooted at the directory you started Carat in, with the current file revealed and marked; the same key focuses the tree when it is open and closes it when it is focused. `:ExplorerFind` reveals the current file in the tree. Inside the tree:

- `<CR>` or `l` opens a file in the window you came from; on a directory `<CR>` and `o` toggle it, `l` expands it, and `h` collapses it or goes to the parent.
- `s`, `v`, and `t` open the file in a horizontal split, a vertical split, or a new tab page.
- `a` creates a file next to the entry, or a directory when the name ends with `/`; `r` renames; `d` deletes a file or an empty directory after asking `y` or `n`. The name is typed on the command line, Enter confirms, Escape cancels.
- `R` refreshes, `H` shows dot files, `-` moves the root up, `C` makes the directory under the cursor the root, `q` closes the tree, and `?` shows these keys.
- `j`, `k`, `gg`, `G`, and the `<C-w>` commands work as in any window; `:q` in the last file window quits even while the tree is open.

The tree draws its folders and file types with the icons below, so it reads well with or without a Nerd Font. Its options live in your configuration:

```
plugin.explorer.width 30
plugin.explorer.side left
plugin.explorer.show_hidden false
plugin.explorer.ignore .git build tmp
```

`side` is `left` or `right`, `show_hidden` lists names starting with a dot from the start, and `ignore` names entries the tree never lists. Add `plugin.explorer.enabled false` to turn the tree off, and bind `<leader>e` to something else, or to `none`, to free the key.

## Icons and Nerd Fonts

The file explorer, the diagnostics, and the plugins draw small icons: folders, file types, error and warning markers. By default they are triangles, bullets, and geometric shapes that common terminal fonts already have, each one cell wide, so no extra font is needed. The `icons` option chooses the set:

```
option.icons unicode
```

`unicode` is the default; `nerd` draws Nerd Font glyphs and needs a Nerd Font, below; `ascii` uses plain characters such as `+`, `-`, `*`, and `!`, and also draws the window separators as `|` and `-`, the progress bar as `#` and `-`, and the bullets, quote bars, rules, and table borders of documentation and the reading view as `*`, `|`, `-`, and `+`, so the whole screen is ASCII. Plugins ask for icons by name, so the option switches every icon in the editor.

To use the Nerd Font icons, install a Nerd Font, select it in your terminal, and set `option.icons nerd`. JetBrainsMono Nerd Font is a good choice.

- macOS: `brew install --cask font-jetbrains-mono-nerd-font`, then pick "JetBrainsMono Nerd Font" in the terminal's profile settings.
- Arch Linux: `pacman -S ttf-jetbrains-mono-nerd`.
- Other Linux distributions: download the `JetBrainsMono` archive from the Nerd Fonts project's releases, unpack it into `~/.local/share/fonts/`, and run `fc-cache -f`.
- Windows: install the font on the Windows side (unpack the same archive and select the font files, then "Install") and choose it in Windows Terminal's profile, so a terminal running Carat under WSL draws with it.

Then select the font in the terminal: in iTerm2, Terminal.app, Windows Terminal, GNOME Terminal, Konsole, Alacritty, WezTerm, kitty, and the others, the font is a setting of the profile or the configuration file; the terminal, not Carat, draws the glyphs. Without a Nerd Font the `nerd` icon cells show boxes or blanks.

## How carat is built with AI

Every change to carat, from a feature to a one-line fix, is written by Claude agents and goes through the same pipeline; a person decides what to build and reads the result. The pipeline is a workflow, `.claude/workflows/deliver-change.js`, whose phases are fixed in code, so no step depends on an agent remembering it. The mechanical agents, the checker, the benchmark, the merger, and the runner, which runs the resume and record starts and sprint planning's bookkeeping starts under its own guard profile, run on the cheapest tier, named by the `model:` line of their frontmatter; the contributor and the closing start run on the mid tier at high effort, named the same way, by the user's decision recorded in `docs/goals.md`, whatever a critical change's rules or an escalation say, so no contributor start uses the session's model; the planner, quality reviewer, and security reviewer run on the session's model. The workflow reads the lane's head itself and refuses a contributor result whose head is not it, such as a placeholder, restarting the start once; a refused head and a self-check of match that the next check contradicts by failing a stage are noted as escalations in the run state, which move nothing.

1. The planner orders the queue. Before a change starts, it reads the metrics history, the findings and proposals earlier runs left, and the goals, and writes the next lane queues, `docs/queue-feature.md` and `docs/queue-backlog.md`, by the rubric of `docs/goals.md`: each item tagged with a tier, T0 (a blocking security finding, a red `main`, a crash) to T6 (advisories), and a size, small, medium, or large, a budget of total tokens, input plus output (and 25 minutes for a small change); each decision citing its tier and a number: a metric, a finding, or the user's request. A brief of three or more independently testable parts or map areas is split into balanced changes, its size estimated one size up when the last two comparable runs of its lane went over their budget, and after a stop at the round limit the planner proposes the split of what is left; a change that edits the merge gate's own rules (`tools/rules.sh`) lands that edit first as its own small change, since `main`'s merge gate judges a branch by `main`'s rules. The planner runs only when the queue needs a decision: a change other than the queue's head, a head item without an estimate, a proposal or finding an earlier run left that no later sprint plan placed, or a periodic security review that failed with no change merged since whose planner read the review runs after the review was recorded (a resume past its plan keeping the last time it read them before the plan, and a review recorded without its time cleared by no merge) and no later whole-tree periodic security review passing, a sprint's diff review never superseding one, as `plan-needed` finds, whatever the brief says; otherwise the next item is taken as written. The queue is a sprint of 6 changes from sprint-17 on (5 before, two of them backlog changes), three features in the feature lane and three backlog changes in the backlog lane, a pipeline change only for a defect (a T0 security fix exempt from both, and a sprint whose section holds a line beginning `The user-approved exception` from the pipeline limit), each item self-contained: its locations, why, a fix outline, the acceptance check, and the headings of the backlog entries it covers; the rest waits in its pool. A planned queue fits its lane's own byte budget, which `plan-apply` keeps by dropping the queue's last Decisions lines or refusing with the bytes over, and `push` refuses a lane queue over it, the planner reading the backlog only at a sprint's end. When a blocking security finding is still open, the run stops so its fix goes first.
2. The contributor implements. It starts at the locations the change edits, which the planner's notes give, else its queue entry or the brief, with no scout or context pack before it (`scout-drop`); when the brief is only the change name, it reads the item in its lane queue itself; no delivery reads or greps the backlog, and findings the change only records there reach it as the planner's notes. It keeps the brief it was given, which every contributor start receives, the package start that pushes included, with no other text relayed from the session, so a request to hold for the user's reading reaches the push; it plans the change with OpenSpec (the brief, a proposal, a design, and tasks under `openspec/changes/`, archived together), starts each new file from its golden example in `docs/examples.md` or the `make new-*` generator that wires it in, reads the Spinel pitfalls once in `docs/spinel-notes.md`, writes the code and its tests, and commits as it goes. Before it returns it checks itself: a test for every behavior the change adds or alters, every document describing that behavior current (README.md, docs/architecture.md, CLAUDE.md, docs/codebase-map.md, docs/compatibility.md, docs/actions.md), and the diff compared against the brief with anything extra named. A short rules card sits at the top of its agent file and is repeated in every contributor start's prompt, beside the edge-case checklist of `docs/contributor-notes.md`. Once its tasks are done, before the archive, it reviews its own whole diff with the quality reviewer's instructions, each finding a task of `tasks.md` fixed in the same session or recorded in the findings file with its reason, and reports the counts as `quality_review`; the workflow refuses an implement result without one, restarting it once, and runs no archive and package step until one is recorded. Then it checks its own head in the same session (`docs/contributor-notes.md`, Checking): the docs lint and the gates by hand, a merge of a moved `main`, and `tools/run_state.sh check <change>`, never backing a commit, each failure fixed and committed and the whole check rerun, at most three runs a start, returning the verdict line as `check`; each run after the first counts in `metric.self_fix`, so the rework fixed in its own session stays visible. It is the only agent that edits the repository.
3. The checker runs the fast stages of `make stages` (`FAST_STAGES`) at once, three at a time by default (`CHECK_JOBS`), in the order they need (the tests after their runner's build, the metrics alone after the builds they read), each with its log, in a throwaway clone outside the working copy, so branch code a stage runs cannot write the hooks, git configuration, or run states the gates read; the clone holds its own copy of the toolchain and no link back to the working copy, and a stage that still writes the working copy or, from a lane, the main checkout, its git directory, hooks, info, configuration, references, or staged files, the user's git configuration, its run state, or the shared toolchain by an absolute path voids the check, the paths listed and kept in the run state as a `security-escape` note: the stage records it wrote are rewritten as not passing so no later check reuses them, and when every path lies under a path of the main checkout's `build/` that another lane's tools are known to write, named by `LANE_WRITTEN` (none by default, since every `build/` directory a lane links in is left out of the scan), seen from a lane, its verdict reads `escaped` and the workflow runs it again with no fix round, at most twice in a row, while any other path, the rest of the main checkout's `build/` and its release binary included, fails the check, its fix round as before; an index refresh, a remote-tracking ref, another lane's commit or close, or the merger's fast-forward of the main checkout to the commit origin's branch names, which the runner reads from origin itself, written meanwhile does not; CI runs the rest of `CHECK_STAGES` on the pull request, and the checker never edits. A stage it recorded counts only at the commit the workflow backs: the last check recorded in the run state, or the head the contributor's own check passed at, when the change leaves `tools/`, the `Makefile`, and `test/runner/` alone (`tools/lane_facts.sh` machinery), so the checker, the independent witness, skips the stages passed there but `diagnose`, which CI leaves out and which skips only at the recorded check, since the contributor's runner is its working tree's copy, and still runs the budget, the benchmark comparison, and the moved check; the runner refuses a dirty tree at its own start too, so one started over an edit records nothing; a claimed pass the runner never recorded only runs the stages, and the checker's verdict is the one recorded. When that claimed pass is at the head and every stage already holds its pass record there (`diagnose` only scoped out), the workflow starts no checker: a runner start runs `tools/run_state.sh carried`, which prints the verdict, the budget line, and the benchmark comparison the checker would have returned, and the workflow records the check itself. `tools/run_state.sh check` refuses any other commit, so no stage record is carried from a commit no check passed, and a stage recorded at any other commit runs again. It runs only the stages the paths changed since `main` need: a documentation-only change runs only the docs lint and the gates, and the tools test runs only when a file it reads changed. After a fix that changes only tests, it reruns only the test stages, the docs lint, and the gates and carries the others. The editor's development build and the test runner's build are skipped when the code they read is the code of their last pass with the outputs it left, so a change to tooling or documents does not compile again what `main` passed; CI still compiles on any path but documentation, runs the docs lint on every pull request, and the tools test only when a file it reads changed; pull requests run `.github/workflows/ci.yml` alone, and a push to `main` runs `.github/workflows/main.yml` alone, which builds and smoke tests the release binary, measures `main`, and warms the compile cache, runs the full checks only when the squash tree differs from the head that passed, and compiles nothing when it equals that head and `main` already compiled its sources. It refuses a tree with uncommitted changes. The workflow builds the check's command lines itself and a start of the checker that runs only them, reading nothing, returns the verdict; the checker reads a stage's log only when that stage failed, never on a pass. After a pass it notes the output tokens spent so far against the budget of the change's size, a sixth of its total-token budget, and the workflow records an overrun for the planner without stopping the run.
4. No reviewer start reviews quality in a delivery (the user's decision of 2026-11-21): the contributor's own step does, before its own check, and the sprint planner's review of the combined diff is the independent quality check. Security findings of any severity in the change's own files go back to the contributor once, in the round of the blocking findings or in one of their own while a round remains after it, and are fixed in place when the fix stays in those files and adds no behavior, each a task of the change's tasks.md; the check and the security review then run again at the new head, but for a round of its own that offered no security finding and whose fix changed only the records-only paths the merge gates accept, `docs/goals.md` never (`tools/run_state.sh settled`): there the check, the security review, and the benchmark stand at the commit they passed at, the run state notes the skip, and no review runs; a finding leaves the findings file only when a reviewer there confirms it fixed. Each finding not fixed in place is written to the change's `docs/findings/<change>.md`, so none is lost and no two changes append to one file; the sprint-end grooming files each of their entries into the backlog file of the first file it names, `docs/backlog/<path>.md` with a leading dot of each part written `_` so no backlog folder is named like a configuration folder (`docs/backlog/_general.md` when it names none, each entry with its `- Also:`, `- Category:`, and `- Added:` lines), and only the sprint-end planning reads the backlog and clears its duplicates and the entries a merged item listed.
5. The security reviewer reviews the whole committed diff for vulnerabilities in every round. It is the most important gate: it can never be skipped, and a High or Medium finding it is confident in blocks the merge until it is fixed.
6. The benchmark: the check's `metrics` stage measures allocations and time per key and Spinel's analysis rounds, and `make metrics-compare` compares them with the figures recorded for `main`: those of the newest merged change without a history row, else the newest row of the two lane histories, ordered by main's merge order. Its figures stay in the lane: run from the main checkout, `tools/run_state.sh` writes them under `tmp/.lane-<change>/build/`, never the shared `build/` another lane's check scans. The figures of `main` are measured once per merge: the benchmark agent builds `main` only when `tools/run_state.sh base-figures` finds none stored for its current commit, then stores them (`base-figures save`, which builds main in `tmp/.base` itself, removing the outputs it reads first and refusing an untracked makefile there, and measures that build with main's own `tools/metrics.sh`, in the shared run state directory), and every later run compares with them through `tools/run_state.sh bench`, building nothing: no more allocations or rounds than the stored figures runs no agent, more block, slower time is reported. Without stored figures, equal allocations and rounds run nothing more and any difference starts the agent, which measures `main` and stores it.
7. Whatever blocks goes back to the contributor, and every later phase runs again on the new commit, at most three rounds before the run stops and asks, a red CI included. The rounds are counted across restarts; a restart after a stop the limit did not cause (a killed stage, a restarted container) gets one more, recorded with its reason. A check that did not finish, killed or superseded by a newer commit, costs no round: it runs detached from the checker, which rejoins it at the same commit, and the workflow starts it again, at most twice in a row, naming the stage and its log. Once the last review passes with nothing blocking, one closing contributor start (mode `close-advisories`) fixes the advisories the run raised that sit in the change's own files and need no new behavior; the check of its commit follows, with the security review again unless its commit changed only records and no security finding was offered, the advisories that review raises go to the findings file with no second loop, and the loop is not a rework round: its advisories closed and left are recorded in the run state and in the last two columns of the history row.
8. The contributor archives the OpenSpec change, edits no file the reviews read (`tools/run_state.sh reviewed-edits` names one, which it restores, recording the finding), commits its own lane's records, the planner's queue from the change's own plan directory `build/plan/<change>/` (`tools/run_state.sh plan-apply`, which leaves the other lane's queue) and the history rows of its lane's changes merged before it (`history`, the other lane's left to that lane's next package step), commits the title and the gated body as the archived change's `pr.md` (`tools/open_pr.sh write`), and pushes the branch once; after that push a quality reviewer of the session model compares the text with the committed diff and the proposal's Out of scope, a claim the diff lacks sending it back for one rewrite pushed with `push --pr-text` (a second push) and a second block stopping the run; the push of a `feature/`, `bugfix/`, `hotfix/`, `release/`, or `chore/` branch runs `.github/workflows/branch-push.yml`, which holds no permissions and runs no repository code, and its completion runs `.github/workflows/open-pr.yml` from main, which checks out main storing no token, its actions pinned by commit, checks with the job's own token that the `AI` environment admits main alone as a deployment ref (`tools/open_pr.sh rule`), so no branch's code runs beside the token, reads the branch's new `pr.md` as data, gates it with main's tools, opens the pull request on GitHub's runners with the environment's `PR_TOKEN`, or sets the one open pull request of this repository on the branch to `pr.md`'s title and body, a fork's on a branch of the same name neither counted nor edited, and reads it back equal by its number; a branch without a new `pr.md` is left alone, and no step pushes a tag or deletes a ref. `tools/open_pr.sh wait` records the number, refusing several pull requests on the pushed commit unless one is the number recorded earlier, since a fork's can share it, and the merger merges only a pull request whose head repository and branch are the change's; the merger returns every check as `workflow, name, status, conclusion`, a name with commas read whole; a resume that finds the push but no number only waits for it. No session creates or edits a pull request with a tool or GitHub's API, since one created or edited from a cloud session gets a footer its network layer appends, and the contributor holds no GitHub tool: a pull request opened by hand gets `pr.md`'s text from the push, and a red scan of the title or body is fixed by committing a new `pr.md` and pushing it as a CI fix. The merger waits for CI, which compares the pull request's measurements with the last push to `main`, without giving up while a check still runs: one merger start waits up to 30 minutes, in the foreground through `tools/ci_wait.sh`, 3, 4, then 5 minutes at a time; a red run goes back to the contributor with its log. A merge takes at most 10 tool calls of work, whatever CI does, and 2 for each wait: the workflow hands the merger its records and the merge gates as one command. On green the merger fetches main by its own refspec and runs, in the delivery's worktree, the merge gates of a fresh worktree of `main` under it, which the branch cannot have edited, once `git fsck` has hashed every object of the shared store and `git diff --quiet`, over the copy's index reset to main's tree by `git read-tree`, has hashed every tracked file of the copy against it, and `git ls-files --others` has found no untracked or ignored file in it, with no `refs/replace` entry standing (the stop failing closed when `for-each-ref` itself fails) and every git of the line run with `--no-replace-objects`, so no object branch code planted, swapped back after the add, or wrote into the copy reaches them, and squash-merges the head they checked with the message `tools/open_pr.sh message` prints, the body of the contributor's `pr.md` at that head and the trailer, passing the full sha the push recorded as `expectedHeadSha`, the head GitHub must find. The merge tool has its own hook: `main`'s guard refuses a merge that is not a squash at the head the push recorded and the merge gates passed at, a message other than the body of the archived change's `pr.md` at that head, one blank line, and the trailer, naming the first line that differs, so the squash commit on `main` keeps the four sections, or while `origin/main` differs from origin's `main`.
9. The retrospective closes the run in one start: it runs the run's last records, flags a run over its size budget with a line starting `under:` or `over:` (the run state keeps the size the planner estimated, so the history row carries it beside the total and output tokens after the queue item is gone), and proposes at most three ways to simplify the workflow, its script, or its agents, each backed by numbers, and writes the report in a fixed shape that names any rule broken. The delivery never reviews the whole codebase itself; its report says when the sprint's last counted change has merged.
10. Sprint planning closes each sprint of six merged changes (five before sprint-17, the user's decision of 2026-11-17 in `docs/goals.md`), counting only the queue's numbered items under a `## Sprint N` heading, their split parts (a name less one trailing letter, such as `-c`, equal to a counted change's name or that name less its own letter), and a delivered name no queue holds, never a T0 item, a change a paragraph starting `The user-approved exception` puts `outside the 3`, one whose item's parenthesis says `beyond the sprint`, or another pool item, its row ending at its last counted change and the not-due line naming each change left out by its reason (unlike `the user-approved exception` inside an item's parenthesis, which lifts only the pipeline limit): the main session starts `/sprint` (`.claude/workflows/sprint-planning.js`) after every merge, and it ends at once, with the line of `tools/run_state.sh review-due`, until the sprint is due. Then the security reviewer, never skipped, reviews the sprint's combined diff, getting one more start over the files it left at its cap, a file the second start names left matched in any spelling (a leading `./`, a line suffix, a worktree prefix). The workflow records each security finding of the reviewer's result in the sprint's run state before the planner, so a planner at its cap loses none, and `tools/run_state.sh note` records an identical security note once, so `/sprint` again adds no duplicate. The planner, in its sprint mode, is the independent quality check since no delivery starts one (the user's decision of 2026-11-22): it reviews the combined diff for correctness and the broad points (style, naming, the layers, duplication across the changes, and docs currency) and reads the security findings against the code, recording nothing: a quality finding it drops is never recorded, a security finding it disputes is recorded again as disputed, never dropped, and one the reviewer missed is returned in its own field, recorded, and counted blocking as the reviewer's would be, the workflow writing each note it returns, and before it each security finding of the reviewer, as one single-quoted shell word, so no finding text reaches the shell, run by the security reviewer in its record mode under its read guard, which stores the text as written and records no review or phase. A quality review the planner leaves at its cap, its `not_reviewed` files named, gets one more start of the quality reviewer over exactly those files, its counts and notes merged into the planner's, and the report's Quality line names how many of those files it reviewed and how many are still left; a review that still leaves files is recorded `partial`, never passed. Every second sprint the whole-tree review of `/review` runs beside them; a sweep that failed to start is recorded as `not-run`. The planner starts only after a complete security review and that sweep, and `groom` and `review-due` hold a sprint whose security review is `partial` or `not-run`, or whose sweep has no result or did not run, so `/sprint` again reviews it anew. The planner, in its sprint mode the only reader of the backlog, then grooms it, duplicates found by `backlog-dups` and decided by the model, a near-same note merged into its entry, `groom` appending its lines so both reasons and locations stay and none is dropped, the oldest 50 entries, which `backlog-oldest` prints, checked against the head for evidence and never removed for their age (the user's rule of 2026-11-21, so `groom` refuses a stale or closed line), one whose named paths are all gone leaving only with a reason saying why its problem no longer applies, entries removed by the headings a merged item listed (`groom` refusing a change outside the sprint or whose queue item lacks the heading), a security entry (one naming security and a severity in any wording, such as security Low or a Low finding of the periodic security review, a planner's dispute, or a severity and confidence pair such as High (8)) leaving only that way or with the commit that fixed it named (one of the sprint's range, not a merge, changing a file the entry names, never gone or a duplicate) and merging only into another security entry, old entries triaged once by the same evidence, and writes the next sprint of 6, its three backlog items the first three batches of `tools/run_state.sh backlog-pick` over the folder `docs/backlog/` and the findings files, which it requires, the oldest `- Added:` date first: entries naming security first, then the oldest, each batch 5 to 10 entries of one code map area (an area under 5 giving only its security entries), an entry a queued item names or the plan's `groom.txt` removes skipped and one whose Location no map area holds reported; after about five backlog runs it compares the backlog lane's history with the feature lane's and proposes a budget, call cap, or tier change only from those figures. Its files wait in `build/plan/` for the next delivery's package step, which runs `tools/run_state.sh history`, `groom`, and then `plan-apply` (the user's decision of 2026-11-22: no records change), so the sprint's records land in that delivery's own pull request: the first to package carries the plan, writing `build/plan/sprint.carrier`, its `history` appending every lane's rows, and the other lane's `groom` stands down while the marker stays until main holds the row, `merge-main` keeping each lane's own queue when the two meet; a blocking sprint security finding, or the plan's security first, holds it until a change planned after the review merged. `groom` applies a plan once (a sprint whose row stands on main is not applied again), checks every removal, writes nothing if one fails, applies the queue, and adds the sprint's row to `docs/sprints.tsv`: its merges, wall minutes per change against the pace of one an hour, total tokens and the runs over their budgets, and first passes. A brief that excludes the planning records sets `records=skip` in its change's run state, and that package step runs no `history` and no `groom`. A review that reaches its cap returns what it covered and is recorded as `partial`, and one that returns nothing as `not-run`, never as passed.

Rules are checked, not remembered. `tools/gates.sh` refuses a commit without its single co-author trailer, a link, an email address, a session id, or a model name in the diff, the commits, or the pull request; a snapshot not written by the test runner; a new file missing from the code map; a new command, binding, option, make target, or process change without this README; a spec change that leaves this README or `docs/architecture.md` as they were, or a process change that leaves `CLAUDE.md`, unless the change's proposal says why; an added or modified spec scenario that no test names; a findings entry removed by any change but one appending the sprint row `groom` writes; a second push without a CI failure to fix; and a merge without the recorded passes of the check, the security review, and the benchmark at the pushed head. One scanner, `tools/scan_text.sh`, reads the forbidden text for every check: the gates at the push and the merge, and the `scan` workflow on each pull request, which runs the base commit's scanner, so a pull request cannot weaken its own check, and reads its title, body, commit messages, and added lines whenever it is opened, edited, reopened, or pushed to, so a footer added to the body after it opens turns the check red and the merger, which merges only over green checks, waits until it is removed. No local commit hook is installed: the gates and the agent guard refuse any `core.hooksPath` and any hook but a sample in `.git/hooks`, since a hook a checkout can write would run code of any branch. Facts are read, not copied: `tools/lane_facts.sh` prints a lane's head, branch, base, push state, uncommitted paths, and last check verdict from git and the check log, and the workflow takes the contributor's head from it, so a head that differs only in form from a committed lane's is noted and kept from git, never refused or restarted.

Documents are budgeted too. `make docs-lint`, a stage of `make check`, keeps `CLAUDE.md` within 30 KiB, each agent file within 8 KiB, `docs/architecture.md` within its budget, and each lane queue within its own budget, 6,976 bytes for the feature lane and 10,993 for the backlog lane (17,969 together), because agents read them on every run; a lane's check reads only its own queue, so the other lane's growth never fails it, while `main` and CI check both, and refuses a link, an address, a model name, hard-wrapped pull request text, a path that no longer exists, or a lane history row whose field count differs from its header's, which `tools/run_state.sh history` keeps equal to the columns it writes by refusing a lane file whose header differs. When `authoring-kit` introduced it, `CLAUDE.md` went from 41,066 to about 30,600 bytes and `docs/architecture.md` from 91,890 to about 87,300, the detail moving to `docs/spinel-notes.md` and `docs/examples.md`.

The run state of a change, `build/pipeline/<change>.json`, records each phase and the commit it finished at, every check stage, the reviews, the pushes, the pull request, and CI. It is written only by `tools/run_state.sh`, which refuses a control character in any key or value, so an interrupted run picks up where it stopped, trusting only the records at a commit of the branch or of `main`; on a resume the check, the reviews, and the benchmark run again, since branch code run by the checks could have written a pass, past the push included, and only the verdicts a start received reach the merge gates' records. A fix round narrows a review to the commits since a pass of the same start, never one only the run state holds, and every High or Medium security finding at confidence 8 or above in the change blocks, a re-rating of an earlier non-blocking one included. The phases and the reviews are recorded by the workflow from what each agent returned, never by the agents, and the merger compares them with what the workflow received before it merges. CI is recorded at the pushed head and the merge only as the pull request's squash commit on `main`, whose subject ends with its number, so a head an agent swapped or mistyped is refused, naming both; the close records the merge, retro, and report phases at that squash commit as the run state resolves it, a different sha the merger reported noted beside it, the merge phase writing the run state's merged commit when none is recorded and refusing one naming another, so `review-due` never misses a merge (it holds the sprint, naming each run state with a merge phase but no merged commit), and runs every record line whatever an earlier one did, reporting a refused one; a review or check still stands after a records-only diff but one touching `docs/goals.md`, whose rules agents act on, the sprint log counting only by the one row `groom` appends for the sprint the plan names. Every agent runs `main`'s `tools/agent_guard.sh` before each shell command or file write, fetched from origin's `main` (its address, which the hook line pins by digest, naming no address, into a new temporary repository with no global or system configuration, every object hashed on arrival, never read from the project's objects, configuration, or local `origin/main`, which branch code can write), and a guard that is missing or fails, or an origin that is not hosted (its https address alone, its ssh and scp forms refused, since the ssh client's own configuration chooses their host) or cannot be reached, refuses the call; it refuses every call while `.git/config` sets a key that runs a command or redirects origin, which the push and merge gates refuse too, with an `origin/main` other than origin's `main`, and while Claude Code's local settings, servers, or instructions file stands untracked at the top of the main checkout, which no agent may write, since it could turn the hooks off for the next agent. Each agent may run only the commands its role needs, read as the shell reads them: the agents that never edit cannot commit, push, call `gh`, write the run state's records, or write a file outside their own directory, and the contributor pushes only through `tools/run_state.sh push`, which runs the gates first. Until that push the commits stay on the local branch, and a run pushes once, plus once per CI fix, once for a review fix, and once for the merge of a moved main: a resume past the push whose check and reviews find a new blocking quality or security review runs one fix round a run, the security review covering the whole diff again, and pushes it with `tools/run_state.sh push --review-fix`; a second such round, or a failed check or benchmark on a resume, stops the run. Findings that arrive after the package step are recorded in the run state and committed by the next change's package step with the metrics row. The checker runs the fast stages (`FAST_STAGES`) and CI the rest on the pull request; a red CI superseded by a green run of the same check of the same workflow file, never one of another file a branch could add, or one only on the scan of the pull request body, costs no fix round.

Every run is measured. `/deliver` records the total tokens and wall minutes of each start, which only the session that ran the workflow sees, with `tools/run_state.sh usage`; the workflow counts the output tokens and tool calls of each phase, whether each gate passed the first time, the rework rounds, and the CI minutes, and stores them in the run state: each metric line holds every figure, run by the workflow's record step after the reviews and at the end and by the merger and the retrospective before their work, so a resumed run keeps them and the run state's totals equal the ones the retrospective is given; the check adds allocations and time per key and the analysis rounds. `/deliver` also records each agent start's input, cache, and output tokens from the Workflow run's transcripts, weighted by its tier's price, per start and per phase (`tools/run_state.sh tokens`), and the closing start the seconds of each CI step (`tools/run_state.sh ci-stages`), beside the merger's calls waiting on CI, in the history's last four columns; later cost changes are judged on the weighted figure. Each agent start is told its cap of tool calls, a figure per kind of start scaled by the size estimate (a fixed one for the starts of sprint planning and the periodic review), and a start that reports more is recorded for the planner; each agent file's `maxTurns` is the ceiling the platform enforces. Each kind of start runs on the model tier and reasoning effort of the workflow's calibration table, recorded beside its figures and in the history's `calibration` column; the table moves one kind at a time by the rule of `docs/goals.md`, and never the security reviewer. A contributor or reviewer stopped by its cap returns what it left, and one stopped by the ceiling returns nothing; either is continued by another start told what is left, at most twice in a row, so the run resumes from the committed work instead of failing. The lane histories `docs/metrics-feature.tsv` and `docs/metrics-backlog.tsv` keep one row per merged change, each in its lane's file (`tools/run_state.sh lane`), written only by `tools/run_state.sh`, and `/status` prints the last row and each gate's first-pass rate.

To start or resume a change, run `/deliver` followed by a change name or a short description in Claude Code (a name that already merged is refused, so a recurring change takes a unique one such as `spinel-bump-<7-char commit>`); `/status` shows the running change and its next phase, `/plan` asks the planner for the next order of the queue with its evidence, `/sprint` closes a sprint once its six changes merged (five before sprint-17), and `/review` runs the whole-tree review now. Outside Claude Code the same checks run with `make check`, `make gates`, `make metrics`, and `sh tools/run_state.sh status`. The plan lives in the repository: `docs/goals.md` is the charter every change serves, the UI first, then code intelligence, security never traded for either, the lane queues the ordered work with the reason for each place and the user's standing decisions, and the lane histories the data behind it. Each delivery runs in its own git worktree, `tmp/.lane-<change>` (hidden, since `spin` reads every visible directory as source), made from `origin/main` by `tools/run_state.sh lane-open` and removed by `lane-close` after the merge or when its run is replaced (a stopped run keeps it for the resume), sharing the main checkout's toolchain, compile cache, run states, stage logs, and plans; its merge gates and benchmark base are worktrees under its own `tmp/`, so two deliveries never share one. The main session may therefore start one feature-lane and one backlog-lane delivery at once, never two of one lane. When main moves while a delivery runs, its implement and fix starts first merge main into the branch (`merge-main`, never a rebase or a force-push), the appended records (the lane metrics, findings, and sprint rows) keeping both sides' rows. On a merge conflict the contributor keeps both sides of an appended file, regenerates a generated one with its `make` target, and stops where both sides changed the same logic; the fix stays in the change and its checks and reviews run again. When GitHub refuses the merge of a green pull request because main moved (the branch behind main or conflicting with it), the same start merges main in the lane, runs the check again, carries the reviews over when `tools/run_state.sh moved` finds no file of the change changed by the merge and the head matching main in every file the change never touched, `docs/goals.md` counted as a file of the change, the names compared as text and a failed comparison running them again (else runs them again), a carried review recorded only at the head of the `moved` record its exit-0 path alone writes, against the commit that review passed at, pushes once with `push --main-moved`, at most once a run, and waits for CI and merges, no new run and no fix round; a conflict where both sides changed the same logic stops the run naming its files. Main-session notes do not survive a reset, so everything a later session needs is in these files: when the project is put on hold, the queue says so in its header, and work resumes with `/status`, which shows the queue and any unfinished run, then `/deliver` with the first item's name.
